# Архитектурное ревью движка и план рефакторинга

Написан 2026-11-17 по просьбе владельца («сделай архитектурное ревью систем, подсистем и в целом организации двигла.
предложи необходимый рефакторинг в виде плана»). **Статус: план R0-R16 — предложение; из находок ревью исправлены шесть малых (10.12), не закоммичено.** Порядок
этапов и открытые вопросы (§8) — решение владельца.

Дополнения: §9 — потоки, физика, игровой режим и цена игровой механики (этапы R12-R14); §10 — дотошное ревью кода
по этапам, с находками по файл:строка (закончено 2026-11-18: десять этапов, сводная оценка в 10.11, исправленное в 10.12).

Как смотрел: скриптами по `sources/` (569 файлов, ~226 тыс. строк; 250 `.cpp`, 319 `.h`) — размеры, граф прямых
`#include "..."` между папками, компоненты сильной связности, транзитивный охват заголовков, глобалы, ключи командной
строки, имена настроек — и чтением ключевых заголовков (`App.h`, `Systems.h`, `Scene.h`, `Renderer.h`,
`RenderableObject*.h`, `SceneRenderer.h`, `SceneFrameData.h`, `SceneResourceBootstrapper.h`, `GraphicsSettings.h`,
`EditorController.h`, `EditorSceneDocument.h`, `Knob.h`, `JsonLevel.cpp`, `EnvironmentRuntime.cpp`,
`SceneRenderer_Graph.cpp`). Числа «методов / полей» класса — грубый regex, порядок величины, не точный счёт. Шейдеры
(191 файл, 40 тыс. строк) смотрел только как контракт с C++. Алгоритмы рендера не оценивал — только границы и
организацию.

## 2. Что устроено хорошо (и что план не должен сломать)

- **Модель потоков проверяется кодом**: роли (`ThreadRole`, `TC_CHECK_GAME / RENDER`), близнецы кнобов (`KNOB`),
  передача на `Sync`, `--rt-audit`. Это уже граница «игра / рендер», ей не хватает только выражения в типах (§3 F2).
- **Реестры вместо обхода сцены**: плавучесть, физика, маска воды, лампы — объект регистрируется сам, пустая сцена
  ничего не платит.
- **Узкие двери**: весь ввод-вывод через `core/vfs` (+ `check_file_io.py`), Jolt только в `sources/physics`, GPU-память
  через `gpu::Create*` (+ `check_gpu_alloc.py`), лог через `LOG_*` (+ `check_logging.py`).
- **Нижний слой настоящий**: `core/math`, `core/vfs`, `core/logging`, `core/memory`, `core/containers`, `input`, `assets`
  стоят вне большого цикла зависимостей.
- **«Одна таблица» там, где её уже ввели**: `OceanWakeKnobs.h`, `VesselKeys`, `BotKeys`, `RaceKeys`, `PlayerKeys` —
  ключ, поле, диапазон, подпись и подсказка в одном месте, файл / `--set` / UI ходят по таблице. Это готовый образец
  для §4 R2 и R9.
- **Документ редактора — источник истины**, правки — команды с undo, поза физики — render offset, а не авторский
  трансформ.
- **Гейты с контрольным плечом** (каждый обязан уметь упасть) и привычка мерить до и после.

## 3. Находки

Упорядочены по тому, насколько они тормозят следующую работу. «Измерено» — из скриптов; остальное — суждение.

### F1. Слоёв нет: почти весь движок — один цикл зависимостей

Измерено: из ~50 подпапок **38 лежат в одной компоненте сильной связности** (все `app/*`, `editor/*`, `rendering/*`,
`materials`, `ocean`, `physics`, `text`, `ui`, `vfx` и `core`, `core/profiling`, `core/task`, `core/threading`).
Обратные рёбра, которые её склеивают:

| Ребро | Сколько | Через что |
|---|---|---|
| `rendering -> app` | 23 | `app/camera/Camera.h` (15), `app/scene/SceneFrameData.h` (4), `Systems.h`, `Scene.h` |
| `materials <-> rendering/core` | 32 / 4 | материалы включают `Renderer.h`, `Renderer.h` включает материалы |
| `core -> rendering / app / input / text` | 6 | `core/Helpers.h` включает `Renderer.h` и `Mesh.h`; `ProfilerScopes.cpp` — `Systems.h` |
| `rendering -> ocean`, `-> physics`, `-> vfx` | 3 / 2 / 4 | `RenderableObject.h` держит `buoyancy::Settings` и `physics::*`; `WindState.h` |
| `physics -> ocean`, `ocean -> app`, `vfx -> app`, `text -> app` | 2 / 5 / 3 / 1 | `OceanReadback`, `Scene.h`, `Systems.h` |
| `app -> editor` | 6 | `App.cpp`, `AppController.h`, `main.cpp`, `JsonLevel.cpp`, `DeveloperWindow.cpp` |

Чем плохо: ни один модуль нельзя собрать, протестировать или понять отдельно; правило «кто кого может звать» живёт
только в голове и в `AGENTS.md`.

### F2. Шесть классов держат на себе всё

Измерено (regex): `Renderer` ~256 методов / ~118 полей (заголовок 1201 строка); `ShadowGpuData` ~185 / ~256 (`.cpp`
5809 строк — самый большой файл); `VirtualShadowMap` ~180 полей; `Scene` ~124 / ~92; `RenderableObject` ~118 / ~60;
`SceneRenderer` ~97 / ~69.

- **`Renderer`** — это одновременно RHI (устройство, очереди, кадры, таймлайн отправки), владелец всех рендер-таргетов,
  ImGui, текст, сервис-локатор менеджеров (материалы, меши, сэмплеры, свет, debug draw) и **транспорт между пассами**
  (`SetVsmShadowSrvs`, `SetGlassPassSrvs`, `SetSdsmPartitionSrv`, `SetLocalShadowPoolSrv`... — «у стекла нет доступа к
  кадру, положим в рендерер»). `Renderer.h` включает `text/`, `ui/`, `materials/`, `lighting/`, `meshes/`, Streamline.
- **`Scene`** — мир игры (объекты, ветер, время суток, лампы, физика, плавучесть), игровая логика (`game::Race`, две
  `VesselCamera`, `PlayerStart`, `RaceCourse`, спрей лодок), настройки уровня (экспозиция, цвет, GTAO, туман, небо,
  облака, bloom) **и** фронтенд рендера (виды, очереди, каскады, клипмап, `ShadowGpuData`, VSM, SDSM и его кэш,
  кэш локальных теней, окклюзия, карта неба сверху, `SceneRenderer`). Половины «игра / рендер» разделены
  комментариями и `TC_CHECK_*`, а не типами: `camera_` / `renderCamera_`, `dirLight_` / `renderSun_`,
  `windState_` / `renderWind_`...
- **`RenderableObject`** — трансформ, render offset, LOD и его гистерезис, чанки, материалы, запись draw-команд,
  теневые PSO, RT-инстанс, **плавучесть, маска воды, физика, судно, GI-маска** и пары полей «игровое / рендерное».
  Поверх — 100 даункастов `As*()` (47 в `rendering`, 31 в редакторе).

Чем плохо: любая новая фича добавляет поля и методы в один из этих классов (так выросли все шесть); любая правка их
заголовка пересобирает полпроекта (F5); потоковая безопасность держится на дисциплине.

### F3. Одна настройка живёт в 5-10 файлах и в 5 параллельных таблицах

Измерено: `App.cpp` — **691 сравнение имени строкой, 616 разных имён** `ns.key` (`ApplySweepValue` строки 458-2113,
`ReadSweepValue` 2113-2440); enum `GraphicsControl` на сотни элементов + `GraphicsSettings.cpp` (2208 строк:
Capture / Apply / JSON / Reset по каждому); `Scalability.cpp kKnobs`; `DeveloperWindow.cpp` — **одна функция на 3674
строки**; `*SettingsJson.h` для уровневых; `KNOB` (263 регистрации) + ещё ~110 обычных глобалов в заголовках.
Примеры охвата одного кноба: `tessy.lodPixelError` — 10 файлов, `skyVis.fallback` — 9, `mieNightScale` — 7.

Чем плохо: это главный источник «кноб есть в UI, но не сохраняется / не сбрасывается / не виден в `--set` /
липнет после `reset_settings`» — половина разделов `AGENTS.md` содержит такую историю. Локальные таблицы (§2) показали,
что решение работает; оно не обобщено.

### F4. Вход в программу и харнессы — монолит

Измерено: `WinMain` — **1602 строки**, 179 ключей в `main.cpp`, 218 всего (ещё в 14 файлах); `App.h` — **50 `extern`**
глобалов командной строки; `App.cpp` 4310 строк; состояние харнессов (`headlessIntent*`, `headlessChat*`) — поля
`EditorController`. Около 27 гейтов и самотестов встроены в exe как режимы запуска.

Чем плохо: `App.h` — самый «широкий» заголовок проекта (тянет 179 проектных заголовков); новый харнесс = правка
`main.cpp`, `App.h`, `App.cpp` и часто `AppController`; список ключей Shipping поддерживается отдельно.

### F5. Заголовки тянут слишком много

Измерено: средний `.cpp` включает транзитивно **59 проектных заголовков, ~14 тыс. строк**. Правка `Renderer.h`
пересобирает **138 из 250 `.cpp` (55 %)** — а с ним `LightManager.h`, `SpotLight.h`, `NightLamps.h`, `FontAtlas.h`,
`ImGuiLayer.h`, `MeshManager.h`, `Material.h`. `Camera.h` (207 строк) тянет 68 заголовков через `SceneView.h`.
`RenderableObjectBase.h` включает `RenderGraph.h` (1862 строки, целиком в заголовке). Кнобы объявлены в заголовках
подсистем: `ShadowSettings.h` — 123 глобала, `VirtualShadowMap.h` — 121, т.е. добавление кноба теней = пересборка
всех, кто видит VSM. `core/task/TaskSystem.h` включают 62 % `.cpp`, и он тянет один из трёх бэкендов (используется
`LockFree`; `TBB` и `Enki` — мёртвый вес в дереве).

### F6. Данные уровня: сырой JSON, ключи читаются во многих местах, два пути применения

- Объект уровня в редакторе — `EditorObject { type, transform, nlohmann::json properties }`; схемы нет. Ключ
  `"buoyant"` упоминается в 13 файлах, `"timeOfDay"` в 12, `"heightFog"` в 9.
- Секции окружения применяются **двумя дорогами**: `JsonLevel::Load` (одна функция на 534 строки) при загрузке и
  `EnvironmentRuntime::Apply` (600 строк, `editor/scene`) при правке — обе зовут одни и те же
  `*SettingsJson::ApplyOverrides`, но порядок, миграции (`MigrateLegacyLocalExposure` в обоих) и побочные действия
  продублированы. Отсюда правило в `AGENTS.md` «ровно два места знают старый ключ».
- Состояние, которое «уровень сказал», лежит и в документе, и в `Scene` (`levelPlayerStart_`, `levelRaceCourse_`),
  с оговоркой «с редактором истина — документ, без него — сцена».
- `app/levels/JsonLevel.cpp` включает `editor/scene/EditorSceneDocument.h` (загрузчик рантайма знает редактор).

### F7. Фронтенд рендера живёт в `app/`, а рендер включает его обратно

`app/scene` — 25 тыс. строк, из них `SceneRenderer*.cpp` ~10 тыс., `SceneResourceBootstrapper.h` — ~50 структур
`*Constants` / `*Handles` (зеркала cbuffer'ов всех пассов) в одном заголовке на 1332 строки, `SceneFrameData.h`
(1171 строка) смешивает **настройки** (`HeightFogSettings`, `BloomSettings`, `GtaoSettings`, `SceneRenderSettings`)
с **данными кадра**. `rendering/` и `vfx/` включают их снизу вверх. `SceneRenderer_Graph.cpp` — 3126 строк ручной
сборки графа функциями по 400-700 строк; пассы достают океан через `Systems::GetOceanSimulation()`, а соседям
передают данные через глобалы (`g_fogDistantSkyLight`, `g_skyIrradianceSrv`, `ocean::g_waterMaskFrame`,
`g_particleDepthWaterSrv`).

### F8. Контракт C++ <-> HLSL держится руками

Измерено: 83 структуры `*CB / *Constants / *Params` в C++ и 67 `static_assert(sizeof...)`; общих заголовков для C++
и HLSL нет; номера bindless-слотов и регистров — числа («слоты 26-31», «t22-t25», `kScenePerFrame` 54), описанные
прозой в `AGENTS.md`. Шейдеры при сборке не компилируются; `check_shaders.py` покрывает compute-шейдеры по списку,
который ведётся руками, хотя полный список перестановок уже записывается (`tools/dist/shader_list.txt`, 264).

Чем плохо: класс ошибок «поле сдвинулось / слот занят / шейдер не собрался и фича молча пропала» ловится только
запуском, а часто — только GBV.

### F9. «Дождаться GPU» как универсальный инструмент

Измерено: ~75 вызовов `WaitForPreviousFrame` (39 в редакторе, 19 в `app`, 16 в `rendering`). Параллельно выросло
несколько собственных «точек простоя»: `ReconcileShadowMode`, `ReconcileShadowCapacity`, `ReconcileSkyOcclusion`,
`ReleaseUnwantedGi`, `ReleaseUnwantedClouds`, `SetBloomFftResidency`, `BeginTargetBatch / EndTargetBatch`,
`ExecuteOrDefer`. Каждая подсистема решает «когда можно пересоздать ресурс» заново; истории зависаний и device
removed в `AGENTS.md` (кольца `ShadowGpuData`, пул кэша теней, смена уровня) — следствие.

### F10. Редактор и dev-UI

`EditorController` — 4850 строк, ~101 поле, `Draw` на 1798 строк с прошитым списком панелей (известная ловушка:
панель зарегистрирована, но не рисуется); MCP-хосты — вложенные классы контроллера; `InspectorPanel.cpp` 5138,
`EditorActionRegistry.cpp` 5165 (конструктор 801 строка), `ContentBrowserPanel.cpp` 4043, `ImportPanel.cpp` 3808.
`ocean/OceanControlsWindow.cpp` (2382 строки UI) лежит внутри модуля океана. `#if WITH_EDITOR` — 303 раза, из них
104 в `app` и 44 в `rendering`.

### F11. Сборка и тесты

Один проект без библиотек: слои не проверяет ни компилятор, ни линкер. Тесты зависят от артефактов Debug-сборки
игры (tlog) — модульного теста, который собирается сам, быть не может; `intent_regression.cpp` вырос до 5232 строк
и проверяет всё подряд (редактор, физику, гонку, glTF, Tessy). Три Win32-конфигурации при требовании x64 / DXR.
Мёртвое: `core/Helpers.h` (ложка и куб из первых дней, при этом включает `Renderer.h`), `Renderer::InitFence`
(«kept for compatibility»), папка `bckp/`.

### F12. Функции-монолиты

Измерено: около 45 функций длиннее 300 строк, 12 — длиннее 750: `DeveloperWindow` (3674), `EditorController::Draw`
(1798), `WinMain` (1602), `SceneStress` (1271), `ContentBrowserPanel::Draw` (1189), `ViewportGizmo::Update` (1025),
`SceneOutlinerPanel::Draw` (1003), `RenderTargetManager::Create` (956), `MeshEditorPanel::Draw` (949), конструктор
`EditorActionRegistry` (801), `ShadowGpuData::Rebuild` (757), `VirtualShadowMap::RecordPageRender` (751). Далее
`BuildGBufferAndAo` (725), `Scene::PrepareViews` (592), `JsonLevel::Load` (534), `Scene::UpdateCascades` (522).

### F13. Архитектура записана в `AGENTS.md`, а не в коде

Файл — около тысячи строк инвариантов («не пиши ограничение в структуру, которую сохраняет редактор», «таблица
дескрипторов ставится раз в кадр», «читай по номеру кадра, не по слоту», «счётчик команд — число, не ~0»). Это
ценная память, но каждое такое правило — граница, которую можно сделать типом, таблицей или гейтом; пока оно проза,
его нарушение находит владелец на экране.

## 4. Целевая картина

Слои, include только вниз (номер — уровень):

```
7  editor        панели, команды, документ, intent/MCP
6  app           окно, цикл, командная строка, харнессы, dev-UI, меню игрока, дистрибуция
5  game          игрок, штурвал, гонка, боты, сессия Play
4  world         объекты и их компоненты, уровень (схема, загрузка), время суток, ветер, реестры;
                 physics, ocean-sim (сбоку, зовут только вниз)
3  render-feat   тени, свет, небо, облака, GI, отражения, пост, видимость, вода, частицы, Tessy;
                 RenderScene (виды, очереди, FrameData) и сборка графа
2  render-core   RenderGraph, таргеты, материалы и шейдеры, меши, текстуры и стриминг, текст, debug draw
1  rhi           устройство, очереди, кадры, отправка, дескрипторы, загрузка, барьеры
0  core          math, containers, logging, memory, vfs, task, threading, profiling, settings (реестр)
```

Три разреза, которые дают эту картину: `Renderer` -> `rhi` + сервисы; `Scene` -> `World` (игровая половина) +
`RenderScene` (рендерная), `Sync` копирует первое во второе; `RenderableObject` -> объект мира + его рендер-состояние
+ компоненты в своих модулях. Плюс два реестра-таблицы: настроек (R2) и ключей уровня (R9).

## 5. План

Каждый этап самостоятелен: после него проект собирается, гейты зелёные, картинка та же. Объём: S — до одной
сессии, M — 2-4, L — около недели работы, XL — больше. Риск — вероятность сломать поведение.

### R0. Замеры в дерево и храповик слоёв (S, риск 0)

- `tools/arch_metrics.py` (метрики этого документа одной командой) и `tools/check_layers.py`: таблица слоёв из §4 +
  список **сегодняшних** нарушений как допуск; новое нарушение = ненулевой код выхода, список может только убывать.
- Готово: оба скрипта в `tools/`, строка в `AGENTS.md` рядом с `check_logging.py`.

### R1. Дешёвые разрезы циклов (M, риск низкий — только перенос и include)

1. `core/Helpers.h`: `ThrowIfFailed` / `GetTimeSeconds` остаются в `core`, примитивы-меши уходят в
   `rendering/meshes/`, include `Renderer.h` убирается; ложку удалить.
2. `Camera`: математика вида (матрицы, джиттер, история) -> `rendering/view/`; ввод и сглаживание мыши ->
   `app/camera/CameraController`. `SceneView.h` перестаёт быть зависимостью камеры.
3. `SceneFrameData.h` делится: структуры настроек -> `rendering/<feature>/...Settings.h`, `SceneFrameData` и
   `SceneRenderSettings` -> `rendering/scene/`.
4. `ProfilerScopes.cpp` (ядро зовёт `Systems`, ввод, текст) -> часть в `app/`.
5. `Systems::Get*` вне `app` и `editor` (13 мест: `rendering`, `ocean`, `physics`, `text`, `core`) -> параметры.
6. `WindState` -> слой ниже рендера (его читают тени и RT); `materials/` признать частью render-core

### R6. `Scene` -> `World` + `RenderScene` (XL, риск высокий; после R1 и R4)

- Порядок: сначала вынести `ShadowViewPlanner` и игровое (без смены владения остальным), затем разделить класс.

## 9. Вторая проходка: потоки, физика, игровой режим, расширяемость под механики

Добавлено 2026-11-17 после вопроса владельца («а ты прям всё чекнул? как организованы потоки, как подключена
физика, как игровой режим сделан, удобство расширения в плане игровых механик?»). Первая проходка (§1-§8) этих
четырёх вещей по существу не касалась: она стояла на графе include и заголовках ядра. Здесь прочитаны цикл кадра
(`App.cpp:4130-4275`), `Scene::Tick` / `Sync`, `core/threading/*`, `physics/PhysicsWorld.h` и структура
`PhysicsWorld.cpp`, `app/game/PlaySession.*`, `PlayerController`, `input/ActionMap.h`, `AppController`, и измерена
история git по коммитам игровых механик. Конкретные дефекты кода по подсистемам — в §10.

### 9.1 Потоки

Как устроено. Игровой поток (он же оконный) выполняет игровую половину кадра N+1 — сообщения окна, ввод, часы, UI,
редактор и MCP, `Scene::Tick`, загрузка уровня — **пока поток рендера рисует кадр N**; затем ждёт его, качая
сообщения окна; запускает шаг физики; делает передачу (`Scene::Sync`, роль `Sync`: никто больше не работает) и
отдаёт кадр N+1 потоку рендера. Отправка в очереди GPU и `Present` — на третьем потоке (RHI). Шаг физики — на
четвёртом, в окне между «кадр рендера готов» и передачей. Задачи (`TaskSystem`) наследуют роль места создания.

Что сделано грамотно:

- **Роль — это фаза кадра, а не id потока** (`ThreadRole.h`): проверки владения срабатывают и при одном потоке,
  детерминированно, до появления второго. Это редкое и правильное решение.
- **`--rt-audit`**: поток рендера хэширует всё, что передача для него заморозила, в начале и в конце кадра, со
  случайными паузами на стыках, и есть самотест, который обязан упасть. Гонку «игра пишет в замороженное» ловит
  инструмент, а не глаз.
- Модель взята у UE целиком и последовательно (кадр задержки, `FFrameEndSync`, близнецы cvar, RHI-поток), с
  измеренной задержкой ввода и с честным A/B каждого шага (`frame.renderThread`, `oneFrameThreadLag`, `rhiThread`).
- Исключение из кадра рендера перекладывается игровому потоку; ожидание качает сообщения (DXGI шлёт окну
  сообщения из `Present`).
- Физика не делит ядра с записью кадра и не держит игровой поток.

Слабые места:

- **G1. Граница проверяется только в Debug и только логом**, и не везде: в `Scene.h` роль проверяют аксессоры камеры,
  солнца, ветра, каскадов и данных кадра, а `CameraExposureRef`, `ColorPipelineRef`, `GtaoRef`, `HeightFogRef`,
  `BloomRef`, `SkyAtmosphereRef`, `TimeOfDayRef`, `Physics()`, `RaceRef()` — нет. Что из этого читает рендер напрямую,
  а что через копию на `Sync`, из заголовка понять нельзя. Это та же находка, что F2: половины надо разделить типами
  (R6), тогда проверка станет невозможностью скомпилировать.
- **G2. Четыре разных механизма передачи «игра -> рендер»**, выбор ручной: копия на `Sync`; близнец `KNOB` с
  трёхсторонним слиянием; отложенная отправка GPU-работы (`ExecuteOrDefer`); «подождать кадр рендера»
  (`WaitRenderForGame`, 27 мест; `WaitForPreviousFrame`, ~75). Очереди рендер-команд нет. Последний механизм
  корректен по построению, но съедает параллельность — это уже мерили (Debug: ожидание на каждой вкладке
  Developer Controls давало 12.6 мс игровой половины против 2.6 мс, когда ждут только рендерные вкладки). Каждое
  новое общее состояние требует решить, каким из четырёх способов его
  передавать, и ошибка не ловится компилятором.
- **G3. Расписание кадра прошито в трёх местах**: лямбды `App::Run`, `AppController::Tick`, `Scene::Tick` / `Sync`.
  Игровая логика (гонка, боты, штурвал) тикается из **UI-фазы** (`AppController::Tick` -> `PlaySession::Tick` ->
  `Race::Tick`), до `Scene::Tick`; её вторая половина (камера судна, спрей, спавн лодок гонки) — внутри
  `Scene::Sync`. Порядок «кто после кого» нигде не объявлен, он следует из порядка строк.
- **G4. Объекты тикаются в `ParallelFor` без объявленных правил доступа** (что объекту можно трогать в `Tick`),
  и вся игровая логика идёт на переменном шаге кадра. Фиксированный шаг есть только у физики, и игровой код на
  него попасть не может (см. 9.2).

Оценка: **грамотно, это самая дисциплинированная часть движка.** Риск не в ошибках модели, а в том, что её
соблюдение держится на знании автора.

### 9.2 Физика

Что сделано грамотно: Jolt виден только в `sources/physics/*.cpp` (заголовок `PhysicsWorld.h` без Jolt, ABI-дефайны
в одном `.props`); объекты приходят через реестр-очередь событий, сцена не обходится; мир без активных тел не
вызывает `PhysicsSystem::Update`; шаг асинхронный с правилом «всё, что тянется к миру, сначала `Join()`»;
детерминированный порядок создания тел; поза — render offset, авторский трансформ не трогается; 16 гейтов, у
каждого плечо, которое обязано выйти неправильным.

Слабые места:

- **G5. `physics::World` — это не «физика», а физика плюс игровые сущности.** В его публичном интерфейсе: игрок
  (`SpawnPlayer`, `SetPlayerInput`, `PlayerEye`, `SetPlayerPossessed`), штурвал и пилоты (`SetHelm`, `SetHelmInput`,
  `SetPilot`), якорь (`ToggleAnchor`), расстановка на стартовой решётке (`PlaceVessel`), данные для кильватера и
  камеры (`VesselHull`, `HelmState`), настройка лодок (`TuneVessels`). В `physics::PlayerSettings` лежат 14 полей
  `test*` — ввод скриптов, включая `testFreeCamera` и `testOrbit` (камера!). Функция настроек называется
  `physics::GameSettings()`. Игровой слой протёк в физический.
- **G6. Общего API тела для игровой логики нет.** Наружу есть только `RayCast`. Нет: силы / импульса / скорости по
  объекту, запросов sweep и overlap, событий контактов и триггеров, хука «перед шагом». Поэтому всё, что должно
  жить на шаге физики, **вписывается внутрь `PhysicsWorld.cpp`**: `PushVessels`, `PullAnchor`, `HoldMooring`,
  `ApplyRollingResistance`, закон руления бота (`VesselInput::steer` — pure pursuit перенесён в шаг, потому что
  игре больше негде выполняться с фиксированным шагом).
- **G7. Физика знает класс рендера океана** (`SetOcean(const OceanRenderable*)`), а не интерфейс «высота воды в
  точке»; тело опознаётся сырым `RenderableObject*`.

Измерено: `PhysicsWorld.cpp` менялся в 6 из 7 коммитов игровых механик (9.4).

Оценка: **подключение Jolt и модель шага — грамотно; граница «физика / игра» — нет**, и это главный тормоз для
новых механик.

### 9.3 Игровой режим

Как устроено: Play In Editor без копии мира. Мир в редакторе стоит (`physics::Settings::simulate` выставляет
`AppController` каждый кадр); сессия меняет только render offset тел и камеру, `Stop` возвращает их; единственная
запись в уровень — `Keep`. `PlaySession` держит режим мыши, possess / eject, штурвал, HUD.

Что сделано грамотно: простота и надёжность — `Stop` не может испортить уровень по построению; одна дорога для
редактора, `--play`, MCP и сборки без редактора; правило уровня для Shipping (`Player Start` -> пешком, нет ->
свободная камера); тестовые входы позволяют гейтам и скриптам пройти реальную дорогу.

Слабые места:

- **G8. Сессия умеет менять только позы тел и камеру.** Сессионного состояния объекта нет: скрыть, уничтожить,
  изменить свойство с откатом на `Stop` — нечем. Создание объектов во время игры — частные дороги: у гонки
  `Race::TakeSpawns` -> `Scene::SyncRaceBoats` (метод сцены, написанный под гонку), у спрея своя. Подбираемый
  предмет, открывающаяся дверь, разрушаемый объект потребуют третьей и четвёртой.
- **G9. `PlaySession` — один класс на всё игровое**: мышь, possess, «взять штурвал», якорь, автопилот, тик гонки,
  панель зрителя, карточка лодки (ImGui), строки HUD. Понятий «управляемое» (pawn), «с чем можно взаимодействовать»
  (interactable), «режим игры» нет: клавиша E — это буквально `world.FindVessel(...)`. Второй вид управляемого
  объекта = правка `PlaySession`, `physics::World`, `Scene::Sync` (камера), `AppController` (HUD).
- **G10. Конкретная игра вшита в слой приложения.** `AppController::Tick` зовёт `scene.RaceRef().DrawResults()`,
  `DrawLabels()`, `DrawBotCards()`, собирает `hudRaceLine_` и `hudBigText_`; `Scene` владеет `game::Race`, двумя
  `VesselCamera`, `RaceCourse`; `App.cpp` разбирает `bot.*`, `race.*`, `player.*`, `vessel.*`. Гонку нельзя
  отключить, заменить или добавить рядом вторую игру, не правя ядро приложения.
- **G11. Ввод без контекстов.** Действия — строки (`"Interact"`, `"Anchor"`) из `bindings.json`, опрашиваются из
  любого места; кто сейчас «слушает» клавишу (UI, пешком, у штурвала, зритель), решают флаг `controls` и ручные
  исключения. Отсюда баг «E берёт штурвал и в том же кадре выкидывает за борт». Скриптовый ввод — параллельный
  канал: каждое чтение клавиши продублировано как `script || (controls && WasActionPressed(...))`, а «скрипт в
  headless-режиме штурвал не берёт» — известная дыра.
- **G12. Игрового UI как слоя нет**: результаты гонки, карточки, меню — ImGui и строки HUD, вызываемые из
  `AppController`.
- **G13. Подсистем, без которых игровые механики быстро упираются в стену, в дереве нет**: звук, скелетная
  анимация, сохранение состояния игры, шина событий, триггер-объёмы с входом / выходом (стартовая зона гонки
  проверяется руками внутри `Race`). Это не дефект архитектуры, а её незаполненные места — но для них сейчас
  нет и посадочных мест.

Оценка: **как режим «запустить и остановить» — грамотно и надёжно; как основа для игры — прототип**: всё игровое
написано напрямую в общих классах, без слоя, в который механика добавляется.

### 9.5 Что добавить в план: игровой слой

**R12. Ввод: контексты и один канал (S-M, риск низкий).** Стек контекстов действий (UI > штурвал > пешком >
свободная камера): действие доставляется верхнему, кто его слушает, и считается потреблённым. Имена действий —
константы, а не строки на месте вызова (опечатка перестаёт быть тихим `false`). Скрипты, MCP и гейты **вбрасывают
действия в тот же канал** — поля `test*` и ветки `script || ...` уходят, дыра «headless не берёт штурвал»
закрывается сама.

**R13. Игровые системы и сессионное состояние (L, риск средний).**

- Интерфейс системы: начало / конец сессии, загрузка уровня, `Tick(dt)`, `FixedTick(step)`, вклад в передачу
  (`OnSync`), свой UI, отладочная отрисовка, строки HUD, свои ключи настроек (через реестр R2) и ключи уровня
  (через схему R9). Гонка, штурвал, игрок, спрей — системы в списке. `AppController`, `PlaySession` и `Scene` зовут
  список, а не `RaceRef()`.
- Понятия «управляемое» и «с чем взаимодействуют»: лодка — первая реализация, а не единственный случай в коде.
- Сессионный журнал: изменения объектов во время игры (видимость, свойства, создание и удаление) записываются и
  откатываются на `Stop` тем же местом, что сейчас возвращает позы. Один API создания и удаления объектов во время
  игры на передаче — вместо `SyncRaceBoats` и частной дороги спрея.
- Явное расписание кадра: фазы (ввод -> игровые системы -> объекты -> плавучесть -> физика -> ... -> передача)
  объявлены в одном месте.

**R14. Физика как сервис для игры (L, риск средний — трогает шаг).**

- Ручка тела по объекту; силы, импульсы, скорость, кинематическое перемещение; запросы луча, sweep, overlap;
  события контактов и триггеров очередью, которую игра читает после шага.
- Хук фиксированного шага: игровая система регистрирует `FixedTick`, вызываемый на потоке шага с доступом только к
  физике и своему состоянию. Лодка, якорь, швартовка, игрок, руль бота переезжают из `PhysicsWorld.cpp` в игровой
  слой **поверх этого API** — `PhysicsWorld` снова становится физикой, а его гейты продолжают их проверять.
- Интерфейс «поверхность воды» вместо `OceanRenderable`.

Порядок: R12 можно делать сразу (не зависит ни от чего). R13 лучше после первого шага R6 (игровое вынесено из
`Scene`). R14 — после R13, по одной сущности (якорь -> швартовка -> лодка -> игрок), с гейтами `vessel`, `world`,
`player` как критерием. Звук, анимация и сохранения (G13) — отдельные фичи, не рефакторинг; но заводить их стоит
уже как системы R13.

### 10.1 Этап 1 — планировщик задач и потоки

Прочитано целиком: `core/task/TaskSystemLockFree.{h,cpp}` (единственный собираемый бэкенд), `core/threading/
RenderThread.{h,cpp}`, `ThreadRole.{h,cpp}`, `Knob.h`; из `core/containers/inl_vector.h` — вставка и проверки.
Не читал: `TaskSystemStress.cpp` (что именно проверяет гейт `--tasksystem-stress`), бэкенды TBB и Enki (не
собираются).

**Вывод.** Написано человеком, который понимает lock-free: очередь — классическая, без самодеятельности; владение
задачей расписано по ссылкам и объяснено в комментариях; ожидание не может зайти во взаимную блокировку по
построению. Слабое место одно и системное: **контракты проверяются `assert`, а отказ молчит** — в Release нарушение
превращается в вечное ожидание, запись за границу буфера или падение без строки в логе.

Существенно:

1. **Зависимость от уже запущенной или завершённой задачи — в Release тихое зависание.**
   `TaskSystemLockFree.cpp:638` и `:653` — контракт `SetDependencies` («цель не отправлена, зависимость ещё не
   запланирована») стоит на двух `assert`. В Release ребро регистрируется всё равно: `pendingDeps_` зависимой задачи
   уже увеличен (`:657`), а `dependents_` зависимости — несинхронизированный массив, который `NotifyDependents`
   (`:178-184`) обходит при её завершении. Если зависимость уже завершилась, уведомить некому: задача никогда не
   станет готовой, `Wait` на ней не вернётся; если завершается прямо сейчас — гонка на массиве. *Проверено* (сценарий
   следует из кода; случается ли он в сегодняшнем графе — неизвестно, Debug-assert молчит). Лечение: в любой сборке
   либо не считать ребро от завершённой задачи, либо `LOG_FATAL`.
2. **Переполнение веера зависимых — `abort()` без единого слова.** `TaskSystemLockFree.cpp:658-664`:
   `assert(false); std::abort();`. Это уже стоило отладки (в `AGENTS.md`: «a bare 0xC0000409 and no log line»);
   вылечено поднятием ёмкости с 4 до 8 (`TaskSystemLockFree.h:50-53`), а причина по-прежнему не называется. Ёмкость —
   константа, граф растёт (сейчас шесть RT-пассов висят на одном `BuildAS`). *Проверено.* Лечение: `LOG_FATAL` с
   числами перед `abort`, а лучше — расти в кучу после восьми.
3. **`inl_vector` в Release пишет за границу.** `core/containers/inl_vector.h:209-217`: `emplace_back` проверяет
   ёмкость только `assert`. Используется в `RenderGraph.h` (18 мест), `RenderContext.h`, `ShadowGpuData.h`,
   `SceneRenderer`. Планировщик проверяет ёмкость сам перед вставкой; остальные вызывающие — предмет этапов 2, 6, 7.
   Этот класс уже дал ошибку (потерянное ребро графа при `DependencyList` на 4). *Проверено.* Лечение: проверка в
   любой сборке (`LOG_FATAL`) — цена одна ветка.
4. **Исключение в задаче проглатывается.** `TaskSystemLockFree.cpp:391-400`: `RunTask` ловит всё, пишет
   `LOG_ERROR_ONCE_PER_MESSAGE` и помечает задачу выполненной; тот, кто ждёт, ничего не узнаёт. Для задачи записи
   пасса это означает кадр, ушедший на GPU с недописанным списком команд. Рядом — правильный образец: исключение
   самого кадра рендера сохраняется и перебрасывается игровому потоку (`RenderThread.cpp:170-178`, `:112-118`).
   *Проверено* поведение `RunTask`; что места, которые бросают (кольцо дескрипторов «THROWS»), исполняются именно
   внутри задач — *подозрение*, проверяю на этапе 2.
5. **Проверки ролей потоков есть только в Debug** (`ThreadRole.h:77-86`; `ThreadRole.cpp:174-176`: «checks compiled
   out (Release)»). Release_Editor — основная рабочая сборка — идёт без них, а Debug-кадр стоит 13 мс. Защита
   работает там, где работают реже всего. И найденное нарушение не останавливает: игровая ЗАДАЧА, дотянувшаяся до
   рендера во время кадра, получает одну строку Error за процесс и продолжает (`RenderThread.cpp:147-153`).
   *Проверено.* Лечение: сравнение `thread_local` стоит наносекунды — оставить проверки в Release_Editor, счётчик
   нарушений в `get_readouts`.

Мелочи:

6. **Пара `submitted_` / `pendingDeps_` — схема Деккера на слабых порядках.** `TaskSystemLockFree.cpp:168-175`
   («уменьшил счётчик, прочитал флаг») против `:679-687` («поставил флаг, прочитал счётчик») с `acq_rel` /
   `acquire`. По стандарту нужен `seq_cst`, иначе оба могут увидеть старое и задача не запустится. На x86-64 это
   корректно, потому что обе записи — `lock`-операции (полный барьер). Движок только x64, так что дефект формальный —
   и станет настоящим на ARM64. *Проверено.*
7. **Вложенное ожидание кадра не качает сообщения.** `RenderThread.cpp:69-75`: `WaitIdle`, достигнутый из
   обработчика сообщения внутри насоса, ждёт `WaitForSingleObject`. Заголовок сам объясняет, зачем насос нужен: DXGI
   может ПОСЛАТЬ окну сообщение из `Present` и ждать ответа. Совпадут — взаимная блокировка. *Подозрение*: нужно
   знать, какие обработчики окна паркуют рендер (этап 10).
8. **Кноб-структура сравнивается `memcmp`** (`Knob.h:61-70`), а `OcclusionSettings` (`OcclusionHistory.h:74-96`)

**Вывод.** Самая продуманная часть движка из прочитанных. Правила кадра выведены из разобранных аварий и записаны
рядом с кодом: слот свободен, когда ОБЕ очереди прошли его значение; забор между очередями — по одному на
производителя; порядок списков на GPU назначается до раздачи работы, а не порядком завершения воркеров; барьеры
компилируются заранее и выпускаются из двух мест. И здесь уже есть то, чего не хватает ядру: `RendererInvariantFailure`
— фатальный контракт в любой сборке. Слабости две. Первая — тот же класс, что на этапе 1, но наполовину закрытый:
часть инвариантов идёт через `RendererInvariantFailure`, а соседние — через `assert` или через исключение, которое
планировщик проглатывает. Вторая — время жизни GPU-ресурсов: общего механизма «освободить после кадра N» нет, вместо
него около 70 полных ожиданий простоя GPU и три самодельные корзины.

Существенно:

1. **Исключение из пула кадра или кольца дескрипторов внутри пасса — не падение, а кадр без пасса.** Пулы
   аллокаторов и списков бросают `std::runtime_error` (`FrameResource.h:152`, `:156`, `:235`, `:239`, `:243`,
   `:263`), кольцо дескрипторов — после `LOG_ERROR` (`DescriptorHeapGPU.h:62-67`). Оба вызываются из тел пассов:
   `Renderer::BeginThreadCommandList` (`Renderer.cpp:1563-1564`), `StageDescriptorTableRange` (`Renderer.h:905`). Тела
   пассов — задачи (`RenderGraph.h:757-759`); ни в `RenderGraph.h`, ни в `app/scene` нет ни одного `try`. Значит,
   исключение ловит `RunTask` (этап 1, п. 4): строка Error, задача «выполнена». Дальше: список пасса не закрыт и не
   зарегистрирован, его заранее скомпилированные барьеры не выпущены (следующие пассы переводят ресурсы из
   состояния, которого не было), а незакрытый список при следующей выдаче из пула не проходит `Reset` — и бросает
   снова (`FrameResource.h:252-264`). Авторы это знают: `Close` проверяется явно, потому что «worker tasks must not
   throw (the task system swallows task exceptions)» (`Renderer.cpp:1610`, `:1668-1669`). В `AGENTS.md` про кольцо
   написано «An overflow THROWS -- a crash»; по коду падение, если случается, — вторичное. *Проверено* (подозрение
   п. 4 этапа 1 подтверждено). Лечение: в этих местах — `RendererInvariantFailure` вместо `throw`; это инварианты
   (ёмкость пула, переполнение кольца), а не ошибки, которые кто-то обрабатывает.
2. **В графе пассов половина проверок ёмкости — только `assert`.** Рядом стоят правильные, в любой сборке
   (`RenderGraph.h:240`, `:367`, `:1047`, `:1776`), а эти — нет:
   - участников CL-группы больше восьми: `assert`, затем `push_back` в `inl_vector` на 8 (`:1792-1793`) — в Release
     запись за границу;
   - деклараций состояний больше 16: `assert`, в Release — молчаливое усечение (`:1779-1783`). Усечённая декларация
     — это барьер, который компиляция не зарегистрировала; авторы сами называют это направление фатальным
     (`:894-899`);
   - цикл в графе: `assert(false)` (`:1675`), в Release пассы цикла молча не исполняются;
   - зависимость с индексом за пределами графа (переданный дальше `kNone`): Fatal с именем пасса есть, но под
     `#ifndef NDEBUG` (`:1755-1771`); в Release ребро молча отбрасывается (`:1820-1823`). Потерянное ребро — уже
     случавшаяся ошибка (дрожание облаков при `DependencyList` на 4);
   - пассов больше `MaxPasses`: `assert` (`:1749`), в Release запись за массив. Риск низкий: `MaxPasses` — это
     `RenderPass::Main_Count`, пасс без имени в enum не добавить.

   *Проверено.* Лечение: те же пять мест перевести на `RendererInvariantFailure`.
3. **Время жизни ресурсов держится на «дождаться простоя GPU».** `WaitForPreviousFrame` (`Renderer.cpp:2041-2066`)
   — около 70 вызовов в 34 файлах; каждый сливает очередь RHI и ждёт оба забора, а с игровой половины ещё и
   паркует поток рендера. Там, где так
   нельзя, написаны три отдельные корзины отложенного освобождения: слоты текстур (`BindlessHeap.cpp:119-140`),
   `TextureRetireBin`, корзина ускоряющих структур (`AccelerationStructure.cpp:586-610`). Общей службы «освободить,
   когда кадр N прошёл» в RHI нет, поэтому каждое новое место выбирает между остановкой кадра и четвёртой корзиной.
   Тот же пробел в `UploadBatch::Submit` (`UploadBatch.cpp:38-55`): очередь держит живым только список
   (`Renderer.cpp:2081`), аллокатор и upload-буферы должен хранить владелец — контракт записан комментарием.

Мелочи:

5. **Ожидание забора не перепроверяет значение.** `WaitFenceOrReport` выходит по любому срабатыванию события
   (`FrameScheduler.cpp:35-36`); событие одно на забор и общее для `WaitForFrame` и `WaitForGpuIdle` (`:173`,

   кадра, `App.cpp:3605`), так что это запас прочности: цикл `while (GetCompletedValue() < target)` закрывает класс.
6. **Переполнение upload-кольца молчит и стоит ресурса в кадр.** Основное кольцо — 4 МБ на слот
   (`FrameScheduler.cpp:157`); сверх него `AllocDynamic` создаёт committed-ресурс не меньше 4 МБ под мьютексом

   (`Renderer.cpp:791-799` разрешает отставание на кадр). Взаимной блокировки нет — забор слота от этого `Present`
   не зависит, — но `Present` простоит до следующего насоса. *Подозрение* (задержка, не зависание).
8. Формальные гонки на диагностике: `nextFenceValue_` читает ожидающий поток, пишет поток RHI
   (`FrameScheduler.cpp:175`, `:232`); `g_asyncComputeLists`, `g_crossQueueWaits`, кольцо `g_submitEdgeRing` пишет

9. Два места подают списки в очередь мимо дороги RHI: `HzbCullSelfTest.cpp:621`, `RtSmoke.cpp:139`. Правило «всё
   через `Rhi().Run`» держится дисциплиной (вызывающих всего пять), проверки вроде `check_gpu_alloc.py` на него нет.
10. `RenderContextPool`: до 64 контекстов оседают в `thread_local`-заначке потока и в общий список не возвращаются
    (`RenderContextPool.cpp:50-59`; `TrimTLS` никто не зовёт, `ResetForFrame` пуст). Рост ограничен, но поток,
    отпустивший много контекстов, держит их, пока другие создают новые.
11. В комментариях остались служебные метки `:contentReference[oaicite:N]{index=N}` (`Renderer.cpp:111`, `:182`).

Сделано грамотно:

- **Слот кадра свободен, когда обе очереди прошли его значение**: одно значение, два забора, объяснено, почему не

Прочитано целиком: `core/vfs/PakCrypto.cpp`, `core/diagnostics/CrashHandler.cpp`, `core/logging/LogQueue.cpp`; из

**Вывод.** Лучший по обработке ошибок слой движка: каждый отказ назван (блок не читается с диска, не сходится CRC,
не проходит аутентификацию, не распаковывается), у каждой проверки при открытии пакета записано, из какой поломки
она появилась, обработчик падений покрывает восемь способов умереть и проверяется гейтом. Криптография собрана
правильно. Находок две, обе про доверие к файлу пакета.

Существенно:

1. **Пакет в сборке с ключом не аутентифицируется.** `vfs::Configure` монтирует каждый `*.tcpak` из `content\`
   (`Vfs.cpp:917-927`); `Package::Open` принимает незашифрованный пакет в любой сборке (`Pak.cpp:480-486`:
   ветка есть только для флага «зашифрован»); приоритет берётся из заголовка самого пакета (`Pak.cpp:475`,
   сортировка `Vfs.cpp:541-548`). Значит, в Shipping файл с любым именем и приоритетом 4 млрд, положенный в
   `content\`, перекрывает любой файл игры: уровни, `config/boot.json`, умолчания графики, готовый DXIL. Шифрование
   даёт тайну исходного содержимого, а не целостность того, что игра загружает. При этом запрет читать файлы вне
   папки игры сделан намеренно (`Vfs.cpp:101-132`, «no loose files») — это та же дверь, только через пакет.
   *Проверено по коду*, вживую не запускал. Нужно ли закрывать — решение владельца (моды против неизменности).
   Закрыть дёшево: в сборке со встроенным ключом отказывать пакету, не зашифрованному этим ключом.
2. **Переполнение в проверке числа блоков.** `Pak.cpp:550`: `entry.blockCount != (entry.size + kBlockSize - 1) /
   kBlockSize` — при `entry.size` от 2^64 − 65535 сумма заворачивается, и запись с нулём блоков проходит `Open`.
   Дальше `Read` принимает любое смещение (`:728`), усекает индекс блока до 32 бит (`:734`), а `BlockAt` индексирует
   таблицу без проверки (`:574`, `:658-665`): чтение за её концом и указатель в произвольное место файла;
   `__except` ловит только ошибку страницы (`:108`), так что это падение. То же число уходит вызывающим как размер
   файла — попытка выделить 16 эксабайт. Нужен специально собранный пакет; по п. 1 его примет любая сборка.
   *Проверено по коду.* Лечение: отказать записи с `size` больше `UINT32_MAX x kBlockSize`.

Мелочи:

3. **Два обработчика `std::terminate` на главном потоке.** `crash::Install` ставит свой (`CrashHandler.cpp:280`), а
   первый `Renderer::BeginFrame` заменяет его на `ReportOnTerminate` (`Renderer.cpp:783-786`; в MSVC обработчик —

   `--pak-keygen` молча выдаст ключ и GUID из нулей.
5. Ошибка страницы ловится только на проходе CRC (`Pak.cpp:99-112`); повторные чтения тех же отображённых байт

Сделано грамотно:

   файл в дереве разработки: короткое чтение даёт `false`, а испорченный счётчик — `bad_alloc` или чтение за
   границей. *Проверено по коду.* Лечение: один проход проверки после чтения (индексы, диапазоны, разумные

Прочитано: из `editor/intent/EditorMcpServer.cpp` (2086 строк) — правило локальности (108-127), снимок экрана

Существенно:

1. **`Origin: null` пропускается.** `EditorMcpServer.cpp:1929`: запрос отвергается, если `Origin` непуст, не

   `text/plain` не нужен preflight (`:108-113`), а `Content-Type` сервер не проверяет. Значит, любая веб-страница,

   `localhost` на любом порту (`:124-126`) — то есть любая страница любого локального веб-сервера. Часть
   браузеров уже спрашивает разрешение на доступ страницы к локальной сети; полагаться на это нельзя.
   *Проверено по коду*, не воспроизводил. Лечение: отвергать запрос с любым заголовком `Origin` (законные
   клиенты его не шлют — это написано в том же комментарии) и требовать `Content-Type: application/json` (тогда
   браузеру нужен preflight, а на `OPTIONS` сервер отвечает 405); при желании — токен сессии в `.mcp.json`.
2. **Редактор — главный потребитель «дождаться простоя GPU».** Из примерно 70 вызовов `WaitForPreviousFrame`

   миниатюр). Каждая правка уровня — остановка обоих потоков и обеих очередей. Это следствие п. 3 этапа 2 и п. 1
   этапа 3, а не отдельная ошибка; но именно здесь R16 и общая функция удаления объектов дадут ощутимый эффект.
3. **Объём и форма.** Пять файлов больше 3800 строк: `EditorActionRegistry.cpp` 5164, `InspectorPanel.cpp` 5137,
   `EditorController.cpp` 4849, `ContentBrowserPanel.cpp` 4042, `ImportPanel.cpp` 3807. Уже в плане (R10).

Мелочи:

4. Сервер обслуживает одно соединение за раз (`:1785-1822`); медленный клиент с таймаутом чтения 10 с держит

Сделано грамотно:

### 10.11 Сводная оценка

Ревью закончено 2026-11-18. Прочитано около 15 тыс. строк из 226 тыс. (7 %), выбранных по одному признаку: где ошибка
стоит дороже всего — планировщик, путь кадра, границы потоков, время жизни ресурсов, разбор недоверенных файлов,
сетевой вход. Эффекты рендера, шейдеры, модели физики и воды, эвристики стриминга и большая часть редактора не
читались; их стерегут гейты, и оценивать их чтением было бы недобросовестно. Код не запускался: все находки —
«проверено по коду», ни одна не воспроизведена вживую.

**Насколько это грамотно сделано.** В трудных местах — грамотно, местами образцово. Автор понимает то, на чём
обычно ломаются самодельные движки: порядок памяти в lock-free очередях, правило освобождения слота кадра на двух
очередях, детерминированный порядок списков, вывод барьеров из объявлений, аутентифицированное шифрование, разбор
двоичного формата с проверкой всего, на что потом опирается чтение. Редкое и ценное качество — культура
доказательства: у решения записана поломка, из которой оно выросло, у гейта есть контрольная ветка, которая обязана
провалиться, у числа — замер. Средние оценки по десяти этапам: корректность 4.0, потоки 4.1, время жизни 3.9,
обработка ошибок 3.6, сопровождаемость 2.9.

**Где слабо.** Слабости не локальные, а системные, и их четыре.

1. *Контракт живёт в `assert` или в комментарии.* Нарушение в Release — молчаливое зависание, запись за буфер или
   кадр без пасса; исключение в задаче проглатывается. При этом правильный механизм в движке есть
   (`RendererInvariantFailure`) и применён примерно в половине мест. Этапы 1, 2, 6, 8.
2. *Время жизни держится на соглашении.* «Дождись простоя GPU» около 70 раз, семь самодельных корзин отсрочки,
   буферы, освобождаемые сразу, запись реестра физики, переживающая объект, слой текстур и материалов, верный
   только «пока рендер стоит». Каждое место по отдельности правильно; ошибкой станет следующее. Этапы 2, 3, 5, 7, 8.
3. *Форма не поспевает за содержанием.* Классы и файлы на тысячи строк, фича размазана по пяти-десяти местам,
   `Scene::Sync` и `ShadowGpuData` знают всё, настройка живёт в пяти таблицах, команда кодируется числом в
   настройках. Это замедляет, а не ломает, — но именно это делает механику дорогой (9.4). Первая проходка, этапы
   3, 6, 7, 9, 10.
4. *Границы доверия.* Два входа извне проверены хуже, чем всё остальное: пакет в сборке с ключом и MCP. Этапы 4, 9.
