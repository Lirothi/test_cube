# Утечка памяти: корзина ретайра RT-буферов никогда не осушалась (2026-09-03)

**Симптом (юзер):** полёт с шифтом по кругу над атоллом на `occlusion_test`, Debug — память
процесса растёт гигабайтами; снапшоты Visual Studio показывают стабильный рост в
`RtSceneAs::Build`.

## Механизм

`AccelerationStructureManager` не может уничтожать буферы, которые GPU ещё читает — одноразовый
scratch первой сборки BLAS и, главное, буферы **выселенного wind-слота** (`PrepareWindSlot`:
deformedVb + три пары BLAS/scratch, семь буферов за выселение). Они уходили в одну плоскую
корзину `pendingScratch_`, освобождаемую целиком, когда `frameNo >= asScratchRetireFrame_`.

Дедлайн `asScratchRetireFrame_ = frameNo + kFrameCount` выставлялся в конце `Build` **каждый кадр,
пока корзина непуста** — не «когда в неё что-то положили». Как только в корзине оказался хоть один
буфер, дедлайн уезжал вперёд каждый кадр и не наступал никогда: всё, что туда попало, жило до конца
сессии. Полёт по кругу над рощей непрерывно втаскивает пальмы в tight-радиус wind-слотов и выселяет
дальние — семь буферов за выселение, десятки выселений в секунду.

Замер после починки (Release, орбита 35 м / 14°/с над центром острова, 60 с): счётчик «всего
отправлено в корзину» растёт **12 → 480 МБ за 55 с (~8.5 МБ/с)** при корзине 0–2 МБ. Это и есть
скорость, с которой старый код копил.

Снапшоты студии показывали `RtSceneAs::Build`, потому что там создаются ресурсы D3D12: студия
видит CPU-объекты рантайма (HeapAlloc), основная масса — в VRAM. Собственные аллокации движка Heap-
профайлер студии не видит вообще: mimalloc подменяет `new/delete` и берёт страницы у ОС сам.

## Починка

`AccelerationStructureManager`: корзина `retireBin_` — записи `{буфер, кадр ретайра}`.
`Retire()` кладёт запись без штампа; `StampRetired(frameNo + kFrameCount)` в конце `Build`
штампует всё, что ретайрилось в этом кадре; `ReleaseRetired(frameNo)` в начале `Build`
освобождает записи, чей кадр наступил. `ReleaseAllRetired()` — только при простое GPU
(`Reset`, `--rt-smoke`). `RetireBinBytes()` / `RetiredTotalBytes()` — для строки памяти.
`asScratchRetireFrame_` удалён.

Проверка: `mem_fly` (Release, `--level=data/levels/occlusion_test.json --cam-pos=0,8,0
--cam-orbit=35,14 --cam-fly-delay=3 --shot-delay=60`), выборка private bytes и GPU dedicated
раз в 2 с:

| t, с | private, МБ | GPU dedicated, МБ | rt.as.bin | rt.as.retired |
|------|-------------|-------------------|-----------|---------------|
| 9    | 2566        | 1696              | 2.0       | 12            |
| 33   | 2568        | 1705              | 0.0       | 302           |
| 61   | 2574        | 1698              | 0.0       | 480           |

Прямой дрейф (`--cam-fly=8,6`) утечку НЕ воспроизводит: камера покидает рощу за 6 с, churn слотов
прекращается. Для колец добавлен `--cam-orbit=<радиус>,<град/с>` (кружит вокруг стартовой
позиции, смотрит по касательной).

## Строка памяти в session-логе

`rendering/core/MemoryReport.{h,cpp}`, раз в 5 с из кадрового цикла `App::Run`, уровень Info,
категория `core`:

```
mem: private 2575 MB (+5) ws 708 | vram local 1696/23370 MB (+6) nonlocal 141 | mi commit 2575 MB | rt.as 72.6 MB | rt.as.bin 0.0 MB | rt.as.retired 151.6 MB
```

* `private`/`ws` — `GetProcessMemoryInfo`; дельта — к предыдущей строке;
* `vram local/budget`, `nonlocal` — `IDXGIAdapter3::QueryVideoMemoryInfo` адаптера устройства
  (по LUID, без проводки через рендерер);
* `mi commit` — `mi_process_info` mimalloc;
* дальше — **провайдеры**: подсистема, владеющая памятью, которую процессные счётчики не
  атрибутируют, регистрирует `RegisterMemoryProvider(name, fn, self)`. Сейчас: `rt.as` (всё, что
  держат AS), `rt.as.bin` (корзина), `rt.as.retired` (всего через корзину за сессию).

Правило чтения: растущий столбец при плоских остальных называет владельца; `rt.as.bin`, идущий
вслед за `rt.as.retired`, — возврат этой утечки. Кандидаты на следующие провайдеры: VSM page pool,
mega-VB теней, texcache, кольца upload'ов.

Наблюдение попутно: `private ≈ mi commit ≈ 2.5 ГБ` уже на старте — почти вся память процесса
живёт в куче mimalloc. Это не утечка, но 2 ГБ CPU-кучи стоит однажды разложить по владельцам.

## Что умеет и чего не умеет mimalloc

Статистика по size-классам (`mi_stats_print_out`, у нас в конце `App::Run`; счётчики блоков
только в Debug-сборке библиотеки), `mi_process_info` (commit/RSS/пик), обход живых блоков
`mi_heap_visit_blocks` без стеков. Трекинга «кто выделил» нет; сборочная опция `MI_TRACK_ETW`
даёт события для WPA, но у нас prebuilt 2.2.5 без исходников. GPU-ресурсы он не видит вовсе —
эта утечка для него невидима по определению.

## На будущее: трасса памяти (как Memory Insights у Unreal)

Строка памяти говорит «сколько» и «примерно кто», но не «какая аллокация». Нужный следующий
шаг — трасса: каждая аллокация/освобождение GPU-ресурса (и, отдельно, CPU-кучи) с тегом
владельца, размером, кадром и стеком, в бинарный поток, который читается оффлайн (Unreal Insights:
LLM-теги + Memory channel). Черновик дизайна:

1. **GPU-ресурсы** — единая точка создания уже почти есть (`renderer->Declarations()`,
   `CreateRawUavBuffer`, `CreateUavBuffer` в rt/): обернуть `CreateCommittedResource` в
   `gpu::Create(desc, tag)` с тегом-владельцем, писать (tag, bytes, heap, frame, ptr) на create и
   release (ComPtr-деструктор → хук через `ID3D12Object::SetPrivateDataInterface` с объектом,
   пишущим release в деструкторе).
2. **CPU-куча** — mimalloc `mi_register_deferred_free`/override `mi_malloc_aligned_at` не даёт
   стеков; практичнее ETW: собрать mimalloc с `MI_TRACK_ETW` (нужны исходники) и снимать WPR
   `-start Heap` / кастомный провайдер, читать в WPA.
3. **Формат/вьюер** — бинарный лог в `logs/` (артефакт, по согласованию), скрипт
   `tools/memtrace.py`: таблица по тегам, дельта между двумя кадрами, топ-стеки роста.
4. **Гейт** — `--mem-readout`: орбита N с, вердикт «МБ/с» по `private`, `vram local` и каждому
   провайдеру, порог; в набор стресс-гейтов.

Не начато; сначала — провайдеры для крупных владельцев (дёшево, ловит класс «растёт при полёте»).
