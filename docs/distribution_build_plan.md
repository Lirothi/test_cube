клика не работает: ImGuiLayer прямо пишет «cwd must be the repo root». Командная строка читается как ANSI (`lpCmdLine`).

Время файла — часть ключа: форма Jolt (`PhysicsWorld.cpp:671-678`, только в памяти), запечка маски воды (`WaterMask.cpp:1409-1425`:
размер + mtime `.mesh.bin`, хранится в `.watermask.bin`), горячая перезагрузка шейдеров (раз в секунду, и в Release).
Существование файла выбирает пермутацию шейдера: проба `.dds` рядом с текстурой материала (`MaterialDataManager.cpp:365, 410`)

**Запись** — тоже в корень репозитория: `graphics_settings.json` (если файла нет, при старте пишется ПОЛНЫЙ снимок,

## 1. Цель и не-цели

**Цель**: одна команда `python tools/build_dist.py --profile=release` (или кнопка в окне §8.4) даёт папку
`dist/<Product>-<версия>/` и zip рядом: exe конфигурации Shipping, нужные DLL, 1-2 пакета `.tcpak` (сжатые, по желанию
зашифрованные), уведомления о лицензиях. Папку можно скопировать на другую машину с подходящей видеокартой и запустить двойным
кликом: ни репозиторий, ни Visual Studio там не нужны, ничего не пишется рядом с exe. Тот же движок в dev-сборках работает с
файлами как сейчас и умеет монтировать пакеты, чтобы дистрибутив проверялся без отдельной машины.

**Не-цели этого плана** (отдельные решения, §10): меню игры и экран настроек, пресеты качества, инсталлятор и Steam, подпись
Authenticode, отправка крэшей на сервер, DirectStorage, моды, локализация. Формат пакета их не закрывает: приоритет
монтирования, удаление файла патчем и выравнивание блоков заложены с D2.

**Честно про шифрование**: ключ лежит в exe, так что это защита от распаковки любопытными и универсальными тулзами, а не от
того, кто готов разбирать бинарник. Так же устроено AES-шифрование pak в UE. Целостность: изменённый блок, блок, переставленный
в другое место или другой файл, — ловятся надёжно (§4). Подмену пакета целиком на старый, но настоящий пакет того же ключа
(откат) это не ловит — не цель.

## 2. VFS — одна дверь для всех чтений

### 2.1. Правила

1. **Рантайм читает только через `vfs::`.** Исключения: редактор и импортёр (они ПИШУТ в `models/` и `data/` и работают
   только с файлами), харнессы, которые в Shipping вырезаны. `tools/check_file_io.py` (как `check_logging.py`): прямое
   чтение — `fopen`, `ifstream`, `CreateFileW`/`CreateFileA`, `_wfopen*`, `LoadFile`, `D3DCompileFromFile`,
   `CreateDecoderFromFilename`, `AddFontFromFileTTF`, `GetFileAttributes*`, `directory_iterator`, `exists`,
   `is_regular_file`, `file_size`, `last_write_time` над путями контента — вне `core/vfs/`, `editor/`,
   `assets/AssetImporter.cpp` и списка мест записи считается находкой, код выхода = их число.
2. **Виртуальный путь = путь от корня контента**, как в JSON сейчас: прямые слэши, без `..`, сравнение без учёта регистра
   (семантика Windows; в оглавлении хранится и исходное написание). Всё внутри — UTF-8, к ОС — только широкие вызовы (`W`),
   командная строка — `GetCommandLineW`. Абсолютный путь (`D:/...`, `--level=C:/x.json`) идёт мимо монтирования прямо в ОС —
   это и есть «прямые пути к файлам»; в Shipping — только если разрешено (§11 п.9).
3. **Монтирование неизменно после старта.** Таблица собирается до первого чтения и потом только читается: никаких замков
   на пути чтения.
4. **Запись не идёт в пакеты.** Всё, что пишется, получает реальный путь ОС через `vfs::WritablePath(kind, rel)`
   (§6). Пакет — только чтение.
5. **Dev-кадр не меняется.** После D1 Release из файлов даёт тот же кадр и лог без новых Warning+, что до него.

### 2.2. API (`core/vfs/Vfs.h`)

- `Mount` по приоритету (первый нашедший побеждает): `Loose(dir)`, `Package(file)`, `User(prefix → dir)` — оверлей с
  ПРЕФИКСОМ: только для того, что игра пишет и потом читает (`data/bot_memory/` → `<user>\bot_memory\`). Оверлея на весь
  корень нет: файл, подброшенный в папку пользователя, не перекрывает контент пакета.
- `bool Exists(path)`, `std::optional<Stat> GetStat(path)` → `{size, version, mount}`: `version` — то, чем сейчас служит
  mtime. У файла — mtime (`FILETIME`) как сейчас; у записи пакета — **64-битный хэш содержимого** (mtime в пакет не попадает:
  `models/**` вне git, копия или `touch` меняли бы пакет). Ключ формы Jolt живёт только в памяти — ему всё равно. Ключ маски
  воды хранится в `.watermask.bin`: сборщик пересчитывает его под `version` меша в пакете (§8.1 п.4).
- `Blob ReadAll(path)` — весь файл в память (`MEM_SCOPE(vfs)`), `std::span<const std::byte>` наружу.
- `File Open(path)` + `bool Read(offset, bytes, dst)` — позиционное чтение из любых потоков без общей позиции и без
  очереди на одном хэндле: пакет **отображается в память целиком** (`CreateFileMapping` + `MapViewOfFile`, только чтение;
  чтение = распаковка/расшифровка из представления, страницы подкачивает ОС), у файла — хэндл на поток. Стриминг текстур,
  хвосты DDS, LOD коллизии идут сюда.
- `void List(dir, pattern, callback)` — для `data/materials/*.json`, шрифтов, уровней.
- Адаптеры для чужих API: WIC из памяти (`CreateStream` + `InitializeFromMemory`), ImGui `AddFontFromMemoryTTF`, DXC include
  handler через `CreateBlob`, nlohmann из буфера. Каждое место описи §0.1 переводится на один из вызовов. Откат на FXC в
  Shipping убирается (там нечего компилировать с диска), в dev идёт через VFS.
- Повторные чтения §0 (`.mesh.bin` 3-4 раза, `.mesh.json` дважды, ядро bloom дважды) через пакет означали бы повторную
  распаковку: на время загрузки уровня — небольшой кэш последних целиком прочитанных файлов (по байтам, `mem:`), или общий
  разобранный результат там, где это проще. Решает замер D2.
- Счётчики: чтения по монтированиям, байты, время распаковки и расшифровки; `get_readouts` блок `vfs`, строка в `mem:`
  (оглавления, кэш блоков и файлов). Shipping: чтение файла мимо пакетов логируется (Warning, один раз на путь), но
  гейт D9 не верит одному этому логу (§9: аудит ОС).

### 2.3. Режимы

| Сборка | По умолчанию | Ключ |
|---|---|---|
| Debug, Release, Release_Editor, Cook | `Loose(корень репо)` — как сейчас (`--vfs=loose`) | `--vfs=packages --pak-dir=<папка>`: только пакеты (+ запись в корень); `--vfs=both`: файлы поверх пакетов |
| Shipping | `User(data/bot_memory/ → %LOCALAPPDATA%\<Product>\bot_memory)`, `patch_*.tcpak` по номеру, `base.tcpak`, `shaders.tcpak` | файлы поверх — только если разрешено (§11 п.9) |

Редактор работает только с файлами: `--editor` вместе с `--vfs=packages` отказывается и говорит почему (он пишет туда, откуда
читает). Корень контента в Shipping — папка exe (`GetModuleFileNameW`), не текущая: ярлык и двойной клик работают.

## 3. Пакет `.tcpak`

### 3.1. Формат

```
[заголовок 4 КБ] magic 'TCPK', версия формата, флаги, имя пакета ("base", "shaders", "patch_001"), id ключа (GUID, 0 = без
                 шифрования), размер блока (64 КБ), смещение/размер/тег оглавления, id содержимого (хэш оглавления —
                 не время и не номер сборки), приоритет монтирования
[данные]         файлы подряд, каждый с границы 4 КБ; файл = блоки по 64 КБ несжатых данных, каждый блок
                 сжат (zstd) или сохранён как есть, если выигрыш < 5 %; при шифровании каждый блок — отдельный AES-GCM
[оглавление]     в конце; сжато и (при шифровании) зашифровано — имена файлов не видны:
                 строки путей, записи {хэш пути, размер, хэш содержимого, первый блок, число блоков, флаги (в т.ч.
                 «удалён» — запись патча, которая прячет файл нижнего пакета)},
                 таблица блоков {смещение, хранимый размер, метод, CRC32C (без шифрования) | nonce 12 + тег 16 (с ним)}
```

- **Блоки по 64 КБ сжимаются и шифруются независимо**, поэтому чтение диапазона распаковывает только покрывающие блоки:
  стримингу мипов и хвостам DDS не нужен весь файл. Маленький кэш распакованных блоков на поток (заголовок DDS, потом его
  хвост — тот же блок), размер в `mem:`.
- **Целостность есть всегда**: без шифрования — CRC32C блока (SSE4.2, ~10 ГБ/с, проверяется при каждом чтении), с ним — тег GCM.
  Битый блок — ошибка с именем файла, а не падение в парсере.
- **Детерминизм**: записи по отсортированным путям, ни времён, ни номеров сборки внутри, фиксированный уровень сжатия,
  синтетический nonce (§4). Один и тот же набор файлов (по содержимому) — один и тот же пакет байт в байт. Изменённый файл
  сдвигает смещения всех следующих, поэтому дельта-патчи по смещениям (SteamPipe) потом попросят выравнивания файлов на
  1 МБ (как `-patchpaddingalign` в UE) — флаг формата, решается вместе со Steam (§10).
- Выравнивание файлов по 4 КБ — под небуферизованное чтение и DirectStorage потом; потеря места ~2 КБ на файл, ~2-3 МБ на всё.
- Поиск: хэш-таблица по FNV-1a-64 нормализованного пути (FNV уже в коде), ~1-2 тыс. записей. Таблица блоков ~30-45 байт на
  блок: ~0.5-0.7 МБ на гигабайт контента.
- Отмена и падение сборки не оставляют полупакета: пакет пишется во временный файл и переименовывается в конце.

### 3.2. Сжатие

Рекомендация — **zstd** (BSD, стандарт для игр, распаковка ~1-1.5 ГБ/с на ядро, степень не хуже zlib): добавить в
`third_party/zstd`, это скачивание стороннего кода — нужно «да» владельца (§11 п.3). Без него — zlib, который уже есть
(`third_party/zlib`): та же степень (замер выше: 71 %), распаковка в 3-4 раза медленнее, ~0.3-0.5 ГБ/с. Метод хранится у
блока, так что «хранить как есть» доступно всегда, и смена метода — пересборка пакета, а не кода чтения. LZ4 / Oodle не
предлагаю: первый жмёт хуже (~80 %), второй платный. Поток стриминга теперь ещё и распаковывает: если D2 покажет, что он
не успевает, блоки одной заявки распаковываются параллельно через TaskSystem.

### 3.3. Что лежит в каком пакете

- `base.tcpak` — контент: уровни, mesh.json/mesh.bin, маски воды, материалы, текстуры (`.dds` вместо PNG, если `.dds` есть),
  пресеты, частицы, шрифты HUD, `input/bindings.json`, экран загрузки, курированные настройки по умолчанию (§6).
- `shaders.tcpak` — скомпилированный DXIL (и исходники HLSL как страховка, §5).
- `patch_NNN.tcpak` — потом: монтируется поверх по номеру, может удалить файл записью «удалён».

## 4. Шифрование

- **AES-256-GCM через Windows CNG** (`bcrypt.dll`): новой зависимости нет, AES-NI. Накладные: 28 байт (nonce + тег) на
  64 КБ блока (0.04 %). Хэндл ключа — свой на поток (`BCryptDuplicateKey`), один общий на 8 читателей не делится.
- **Ключи**: мастер-ключ 256 бит → HKDF-SHA256 → два подключа: `K_enc` для AES и `K_nonce` для HMAC. Один ключ на две роли
  не идёт.
- **Nonce синтетический, от того, что шифруется**: первые 12 байт HMAC-SHA256(`K_nonce`, AAD ‖ хранимые байты блока — уже
  сжатые или сырые, ровно то, что уходит в AES). Разные байты под одним ключом не получают один nonce ни в одной сборке,
  какой бы уровень сжатия или решение «хранить как есть» ни поменялись; одинаковые — дают одинаковый шифротекст (это и есть
  детерминизм, утечка — только «блок не изменился»). Nonce хранится в таблице блоков: до расшифровки его не вычислить.
- **AAD** (аутентифицированные, не шифруемые данные) = {имя пакета, версия формата, хэш пути, индекс блока в файле, метод,
  несжатый размер}. Блок, переставленный в другое место, другой файл или другой пакет, не проходит тег. Хэш пути, а не номер
  файла: добавленный файл не перешифровывает остальные.
- **Шифруются оглавление и все блоки** пакетов, если `encrypt` профиля включён (§8.0). `--pak-verify=<file>` проверяет всё
  офлайн.
- **Где ключ**: генерирует `build_dist.py` при первом запуске (`BCryptGenRandom`), хранит **вне репозитория**
  (`%USERPROFILE%\.test_cube\pak_key.json`: ключ + его GUID; путь — §11 п.4) и печатает GUID. Shipping-exe получает ключ
  сгенерированным заголовком (`sources/core/vfs/generated/PakKey.g.h`, в `.gitignore`): разрезан на куски, XOR-маски,
  собирается в момент монтирования и затирается. Dev-сборки читают зашифрованный пакет, только если ключ задан
  (`--pak-key=<file>` или переменная окружения) — иначе честная ошибка «пакет зашифрован ключом {GUID}, ключа нет».
- GUID ключа в заголовке: exe отказывается от пакета чужого ключа с понятным сообщением.
- Позже, по желанию: подпись оглавления ECDSA P-256 (тоже CNG) закрытым ключом, который никогда не уходит с машины
  сборки, — «пакет изменён» против модов. Не в этом плане.

## 5. Шейдеры в дистрибутиве

1. **Идентичность кэша без абсолютных путей**: (виртуальный путь, точка входа, стадия, цель, флаги компиляции, define-ы) →
   ключ; хэш исходников и include — отдельно, для инвалидации в dev. Чтение исходников и include переводит на VFS шаг D1
   (поведение то же); D4 меняет идентичность и цель. В Shipping из горячей перезагрузки убирается только опрос файлов раз в
   секунду — сам путь пересборки PSO остаётся: им ручки (`raster.bindless`) пересобирают пайплайны.
2. **Фиксированная цель в Shipping**: один набор блобов на все GPU — минимальная поддерживаемая модель. Рекомендация SM 6.6
   (бесшовный bindless им и требуется). D4 начинается с проверки: собрать всё под `*_6_6`; если какой-то шейдер просит 6.7,
   минимумом становится 6.7. Флаги — Release (`-O3 -Qstrip_debug`), из какой бы сборки ни варили: Debug-флаги в
   идентичности дали бы промах на каждом запросе Shipping.
3. **Список пермутаций записывается, проверяется глазами и лежит в git** (`tools/dist/shader_list.txt`): сборка компилирует
   ровно его, поэтому она детерминирована; обновление списка — отдельный режим `record` (§8.3), а не часть каждой сборки.
   Записывает **Release** (те же define-ы, что у Shipping: `TC_SHIPPING` ничего в рендере не меняет — правило) с ключом
   `--shipping-sim` (курированные настройки по умолчанию, пустая `--user-dir`, фиксированная цель шейдеров) и
   `--shader-record=<файл>` / `--vfs-record=<файл>`: каждый поставляемый уровень (загрузка, Play от Player Start, гонка, день и
   ночь) **по рукам**: разрешения 1920x1080 / 2560x1440 / 3840x2160, режимы DLSS, принудительно «без mesh shader», «без RT»
   (если RT не обязателен по минимуму §7), bindless вкл/выкл. Чего игрок не достанет (отладочные define-ы океана,
   wireframe), в Shipping не достижимо.
4. **Страховка (рекомендация)**: в `shaders.tcpak` лежат и исходники HLSL (зашифрованные вместе с пакетом), рядом с exe —
   `dxcompiler.dll` + `dxil.dll` (16 МБ; `dxcompiler` нужен всё равно — отражение). Пермутация, которой нет в пакете,
   компилируется на месте DXC, кладётся в кэш пользователя и пишет Warning `shader permutation not cooked: ...` — игра не
   теряет пасс. Гейт D9 требует ноль таких строк. Без страховки (§11 п.5) промах = Error с именем и пропущенный пасс.
5. **PSO-кэш** — в папке пользователя (§6), по драйверу, как сейчас. Первый запуск на новой машине собирает PSO на лету:
   D4 меряет, сколько это стоит при первом входе в уровень; если много — прогрев за экраном загрузки отдельным шагом.

## 7. Конфигурация Shipping

- **`Shipping|x64`** = Release + `TC_SHIPPING=1`, `/LTCG`, PDB генерируется, но не поставляется: он архивируется в
  `dist_symbols/<версия>/` (`tools/symbolize.py` и WinDbg читают оттуда). В sln — свои отображения для четырёх third-party
  проектов и `model_reaper`, mimalloc и прочие пути по `$(Configuration)` прописаны явно (`lib\Release`). Define-ы Jolt
  (`JPH_EXTERNAL_PROFILE` и др.) те же, что в Release: они задают ABI, `RegisterTypes` падает при расхождении. x86 — удалить из sln.
- **`Cook|x64`** = Release_Editor (WITH_EDITOR: пишет маски воды, есть DXC) с выходом в `x64/Cook/`. Сборщик всегда этот exe:
  его не держит открытый редактор (LNK1104, как было с `model_reaper`), он не Debug (флаги шейдеров) и всегда собирается в
  той же сборке, что и Shipping (версия формата пакета, масок, правила обхода совпадают).
- **`TC_SHIPPING` не трогает рендер** — только UI, CLI и диагностику. Иначе запись пермутаций в Release (§5 п.3) не про Shipping.
- **Вырезается**: все харнессы и офлайн-режимы `main.cpp` (`--scene-stress`, `--physics-gate`, `--tessy-upgrade`,
  `--reimport-*`, `--import`, `--uv-density`, `--lod-report`, `--water-mask-lid`, `--mem-*`, `--log-stress`, `--rt-*`,
  `--trace`, `--memtrace`, `--set`, `--sweep` ...), Developer Controls (F1), инспектор текстур, окно океана, профайлер-оверлей
  и F11, отладочные F-клавиши и Ctrl+цифры, опрос шейдеров на диске, откат на FXC. **Остаётся** (рекомендация, §11 п.6):
  `--window`, `--level`, `--log-level`, `--user-dir`, и для гейтов — `--shot`, `--shot-delay`, `--cam-pos`, `--cam-rot`,
  `--wind-freeze`, `--time`, `--play`, `--crash-selftest`. Профайлер: `PROF_ENABLED 0`, если собирается, и замер — что это
  даёт кадру.
- **Старт**: уровень `bootLevel` профиля (§8.0), по `startMode` сразу в Play от его Player Start (§11 п.2), экран загрузки.
- **Проверка железа до создания всего остального**: D3D12, SM 6.6 (или что решит D4), binding tier 3, DXR 1.1 (inline
  RayQuery: решить, обязателен ли RT или есть путь без него — `skyVis.fallback` уже есть), mesh shader не обязателен
  (откат есть). Не хватает — MessageBox с человеческим текстом («видеокарта не поддерживает ..., нужен драйвер не старше
  ...») и строка в лог, а не падение. То же для «device removed» в игре: сообщение «обновите драйвер», путь к логу.
  **Windows 10**: встроенный рантайм D3D12, по всей видимости, не даёт SM 6.6 — проверить в D6; если так, Agility SDK
  (§11 п.7) обязателен, а не «потом». На Win10 и старых Win11 работает путь старых барьеров — он в гейты (§9).
  Список поддерживаемого железа — честно: проверено только NVIDIA.
- **Крэши**: обработчики на КАЖДОМ потоке, а не на одном — `std::set_terminate` в начале каждого нашего потока (TaskSystem,
  IO стриминга, RHI, шаг физики, рендер) и TBB (`task_scheduler_observer`), плюс `signal(SIGABRT)`,
  `_set_invalid_parameter_handler`, `_set_purecall_handler`, `SetUnhandledExceptionFilter` и векторный обработчик для
  переполнения стека (дамп с отдельного потока: на своём стеке места нет). Дамп — `MiniDumpWriteDump` (с косвенно
  указанной памятью, ~1-5 МБ) в `crashes\<дата>_<pid>.dmp`, Fatal в лог с синхронным сбросом (уже умеет), MessageBox с путём.
  **Чего это не ловит**: `__fastfail` и /GS (0xC0000409 — частый класс в этом проекте) минуют все обработчики в процессе;
  их ловит только WER или внешний процесс. Первый шаг — код выхода и последние строки лога в отчёте; дамп таких падений —
  `WerRegisterRuntimeExceptionModule` или внешний наблюдатель, с инсталлятором (регистрация в HKLM) — §10.
  Дамп + PDB из архива символов = стек.
- **Версия**: оркестратор пишет `sources/app/BuildVersion.g.h` (версия, номер сборки, git-хэш, `-dirty` при незакоммиченном,
  дата; в `.gitignore`), dev-сборки — `0.0.0-dev`. `.rc` с `VERSIONINFO` и иконкой (иконка — §11 п.1), манифест: `PerMonitorV2`,
  `longPathAware`, `supportedOS` Win10/11, `activeCodePage UTF-8` — в манифесте ВСЕХ конфигураций, а не только Shipping, иначе
  dev не проверяет то, что получит игрок. Строка версии — в заголовке сессии лога и в заголовке окна.
- **DLL**: рядом с exe ровно те модули, которые игра загрузила из своей папки во время прогонов записи (оркестратор берёт их
  список из `EnumProcessModules`, а не руками): по коду сейчас это `sl.interposer`, `sl.common`, `sl.dlss`, `sl.pcl`,
  `nvngx_dlss`, `dxcompiler`, `dxil`, `tbb12` и VC++ runtime (минус ~70 МБ против Release-папки).
  `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_APPLICATION_DIR | SYSTEM32)` в начале `WinMain` и проверка подписи
  Streamline (`sl_security.h` — требует отложенной загрузки `sl.interposer`). VC++ runtime — рядом с exe (app-local из Redist
  VS: разрешено, zip работает без установки) или `vc_redist.x64.exe` в инсталляторе потом (§11 п.8). Переход на `/MT` не
  предлагаю: mimalloc и TBB — готовые `/MD`-сборки.
- **Agility SDK** (§11 п.7): `D3D12Core.dll` в `D3D12\` рядом с exe и экспорт `D3D12SDKVersion` / `D3D12SDKPath` — фичи рантайма
  перестают зависеть от сборки Windows игрока. Скачивается с NuGet — нужно «да».
- **Streamline `applicationId`**: заглушка работает, для публичного релиза DLSS NVIDIA выдаёт настоящий id (бесплатно) —
  вписать, когда дойдёт до публикации.

## 8. Сборщик, оркестратор и окно сборки

Три входа в одну сборку: окно в редакторе (§8.4) и MCP — для человека и для меня; `tools/build_dist.py` — оркестратор, который
делает работу и годится для командной строки; `x64/Cook/test_cube.exe --cook` — та часть, которой нужен движок. Все трое
читают один и тот же профиль (§8.0), поэтому сборка из окна и из консоли с тем же профилем даёт те же байты.

### 8.0. Профиль сборки `tools/dist/<имя>.json`

Профили лежат в git: что именно поставляется — решение, а не настройка машины. Два с самого начала: `test` (без шифрования,
быстрое сжатие, без zip и архива символов — проверить, что собралось) и `release`.

```json
{
  "product": "test_cube",
  "version": "0.1.0",
  "levels": ["data/levels/wind_test.json"],
  "bootLevel": "data/levels/wind_test.json",
  "startMode": "play",
  "include": ["fonts/*.json", "fonts/*.tga", "input/bindings.json", "data/loading_screen.jpg", "data/materials/*.json"],
  "graphicsDefaults": "tools/dist/graphics_defaults.json",
  "shaderList": "tools/dist/shader_list.txt",
  "recordArms": {"resolutions": ["1920x1080", "2560x1440", "3840x2160"], "dlss": ["off", "balanced"],
                 "noMeshShader": true, "noRt": false, "bindless": ["on", "off"]},
  "compression": "zstd:19",
  "encrypt": true,
  "shaderSources": true,
  "allowLoose": false,
  "zip": true,
  "symbols": true,
  "out": "dist"
}
```

Правила, которые проверяют и окно, и скрипт: `bootLevel` входит в `levels`; уровень существует и разбирается; у `release`
`version` растёт от сборки к сборке (номер сборки добавляется сам и хранится в `dist/build_history.json`, не в профиле; у
`test` можно повторять); `--levels=`, `--version=`, `--no-encrypt` в командной строке переопределяют профиль на одну сборку и
попадают в отчёт. `include` копируется как есть, **по нему не обходят зависимости**: текстуры попадают только от материалов,
которые использованы на поставляемых уровнях (иначе все 670 МБ DDS легли бы в пакет). В пакет попадают только перечисленные
уровни и их зависимости, поэтому любой список уровней внутри игры (`vfs::List("data/levels")`, будущее меню) сам видит ровно
собранное. Пресетов качества пока нет (§10): когда появятся, их список добавится в `recordArms`.

### 8.1. `x64/Cook/test_cube.exe --cook=tools/dist/<профиль>.json --cook-out=<папка>`

1. **Обход зависимостей движком**: от каждого поставляемого уровня — каждая строка в JSON, которая называет существующий файл
   от корня, рекурсивно по `.json`; материалы по имени → `data/materials/<имя>.json`; правила производных путей §0.1 (`.dds`
   вместо `.png`, `.mesh.json`/`.watermask.bin` рядом с `.mesh.bin`, сиблинги неба). Плюс `include` профиля как есть.
2. **Зашитые в код ассеты**: объединение с последним `--vfs-record` прогонов записи (§5 п.3, лежит рядом со списком шейдеров
   в `tools/dist/`) и статический поиск строковых литералов-путей в `sources/` (без комментариев и без `editor/`: PNG океана,
   каустики, ядро bloom по умолчанию, `sphere.mesh.bin`, корона солнца). Найденное только в литерале и не открытое ни одним
   прогоном — предупреждение в отчёте.
3. **Отчёт** `dist/<...>/cook_report.json` (артефакт сборки, не лог): каждый файл, кто на него сослался, размер до/после;
   **ссылка на несуществующий файл = ошибка сборки**; файл из `import_staging/` — предупреждение («поставляемый ассет живёт в
   staging»); лицензия ассета из CREDITS.md рядом с каждой моделью, ассет без известной лицензии (`rocks`) — ошибка
   профиля `release`.
4. **Производные данные**: маска воды для каждого корпуса с `waterMask`, у которого нет подходящей запечки, строится; ключ
   каждой маски в пакете пересчитывается под `version` меша в пакете (§2.2). Список таких ассетов — в отчёте.
5. **Шейдеры**: компилирует `shaderList` под фиксированную цель с флагами Release (§5); **пакеты** (§3, §4), `--pak-verify` по
   каждому, повторная сборка в памяти и сравнение байт — детерминизм.

### 8.2. `tools/build_dist.py`

Одна команда, по шагам с остановкой на первой ошибке и сводкой в конце: `git status` (незакоммиченное → версия с `-dirty`),
MSBuild `Cook`, `Release` (для прогонов записи) и `Shipping` (тот же байт-в-байт вызов, что разрешён в настройках), `--cook`,
сборка папки, копирование DLL по списку загруженных модулей (§7), `CREDITS.txt` + `THIRD_PARTY_NOTICES.txt` (лицензии
third_party и Streamline/DLSS, DXC, TBB, mimalloc — недостающие тексты добавить в репо), `README.txt` (требования, где логи и
сохранения), `manifest.json` с SHA-256 каждого файла дистрибутива, архив символов, zip. Всё пишется во временную папку и
переименовывается в конце: отмена не оставляет полдистрибутива. Флаги: `--profile=<имя>`, `--levels=...`, `--version=`,
`--no-encrypt`, `--mode=check|record|content|full` (§8.3), `--skip-build`, `--out=`, `--progress=json` (по строке JSON на
событие в stdout: этап, доля, сообщение, предупреждение, ошибка с файлом — это читают окно и MCP).

```
dist/<Product>-<версия>/
  <Product>.exe
  dxcompiler.dll  dxil.dll  tbb12.dll  sl.interposer.dll  sl.common.dll  sl.dlss.dll  sl.pcl.dll  nvngx_dlss.dll
  msvcp140.dll  vcruntime140*.dll        (точный список — загруженные модули, §7)
  [D3D12/D3D12Core.dll]
  content/base.tcpak  content/shaders.tcpak
  CREDITS.txt  THIRD_PARTY_NOTICES.txt  README.txt  manifest.json
dist/<Product>-<версия>.zip
dist_symbols/<версия>/<Product>.pdb  cook_report.json
```

Размер: контент wind_test по описи — оценка 0.4-0.6 ГБ в пакете, DLL ~100 МБ; точное число даст первый отчёт D5.
`dist/` и `dist_symbols/` — в `.gitignore`.

### 8.3. Режимы

| Режим | Что делает | Время (оценка, уточнит D5) |
|---|---|---|
| `check` | обход зависимостей выбранных уровней, предпроверки §8.4, размер до сжатия и оценка после — без сборки и без прогонов | секунды |
| `record` | сборка Release, прогоны записи по рукам `recordArms` (§5 п.3), новый `shader_list.txt` и список открытых файлов — **diff против лежащего в git** на просмотр, а не молча | минуты-десятки минут: прогоны уровней |
| `content` | `check` + шейдеры по списку + пакеты + сборка папки; exe Shipping берёт уже собранный | минуты |
| `full` | MSBuild `Cook` / `Release` / `Shipping` + `content` + проверки §9, которым хватает секунд (`--pak-verify`, запуск exe из папки на `--shot`) + zip и символы | + сборка |

### 8.4. Окно «Build Distribution» в редакторе

Level Editor > File > **Build Distribution…** (Debug и Release_Editor; в Release окна нет — только консоль). Панель регистрируется
И попадает в список `drawPanel` в `EditorController::Draw` (AGENTS: зарегистрированная, но не нарисованная панель включается
из меню и никогда не появляется).

1. **Профиль**: выбор из `tools/dist/*.json`, «Сохранить», «Сохранить как…», несохранённые изменения профиля видны. Продукт,
   версия (кнопка «+0.0.1»), папка вывода.
2. **Уровни**: таблица `data/levels/*.json` (поиск по имени) — галка «в сборку», радиокнопка «старт», число объектов, размер
   зависимостей до сжатия и оценка после (обход только по JSON, считается в фоне при открытии окна и при смене галки),
   сколько файлов уровня — общие с уже отмеченными (сколько он добавит на деле), значки проблем: ссылка на отсутствующий файл,
   ассет из `import_staging/`, ассет под NC-лицензией или без известной лицензии. «Все» / «Ни одного». Внизу итог: уровней,
   файлов, МБ до/после.
3. **Содержимое**: список `include` (правка, добавление по маске), что попадает всегда (шрифты HUD, привязки, экран загрузки),
   руки записи (`recordArms`), когда последний раз обновлялся `shader_list.txt` и сколько в нём строк.
4. **Параметры**: шифрование и **состояние ключа** (найден, GUID, путь; нет — кнопка «Создать ключ» с предупреждением
   сохранить копию: без ключа старые пакеты не прочитать), сжатие, исходники шейдеров как страховка, файлы поверх пакетов,
   zip, архив символов.
5. **Предпроверки** (перед любым запуском, кнопка «Проверить» = режим `check`): несохранённые правки открытого уровня — сборщик
   читает файлы с диска, правки в памяти в пакет не попадут («Сохранить и продолжить» / «Продолжить без них»);
   незакоммиченные изменения в git (предупреждение, версия получит `-dirty`); отсутствующие файлы (ошибка); ассеты из staging,
   NC- и неизвестные лицензии (предупреждения; неизвестная у `release` — ошибка); найден ли MSBuild; место на диске; ключ, если
   шифрование включено; уровень выбран в `levels`, но в `shader_list.txt` нет его прогона — предупреждение «обновите запись».
   Ошибка блокирует кнопки запуска, предупреждения — нет.
6. **Запуск**: «Обновить запись» (`record`), «Собрать контент» (`content`), «Полная сборка» (`full`). Сборка идёт отдельным
   процессом (`python tools/build_dist.py --progress=json ...`), редактор продолжает работать; exe сборщика — `x64/Cook`, не
   exe редактора, так что окно в Debug-редакторе собирает те же байты, что консоль. Этапы списком с временем каждого, общая
   полоса, хвост лога, «Отмена» (дерево процессов сборки — job object, как у llama-server: закрытие редактора убивает и
   сборку; результат при этом не появляется — всё во временной папке). Ошибка — с файлом и тем, кто на него сослался, щелчок
   выделяет объект, если уровень открыт. Прогоны записи и `--shot` — headless-процессы на той же видеокарте: пока они идут,
   кадр редактора медленнее, окно об этом пишет.
7. **Результат**: размер по пакетам и по уровням, 20 самых больших файлов, предупреждения, кнопки «Открыть папку»,
   «Запустить сборку» (exe из папки дистрибутива с `--user-dir` во временную), «Прогнать гейт §9» (дистрибутив на чистом месте),
   «Открыть отчёт».
8. **История**: прошлые сборки из `dist/build_history.json` — версия, номер, профиль, git-хэш, дата, размер, итог гейта.

**MCP** (по правилу AGENTS «сначала MCP, не хватает — расширь»): `build_dist {profile, levels, bootLevel, version, mode, encrypt}`
→ id задачи (отказ во время Play, при занятой сборке, при уровне вне списка, при `bootLevel` вне `levels`) и
`build_dist_status {id}` → этап, доля, ошибки и сводка отчёта, как `import_status`. Гейт — случаи отказа в
`TestMcpDrivesTheSameRoad` и режим `check` на тестовом уровне.

## 9. Гейты

| Гейт | Что доказывает | Контрольная рука (должна упасть) |
|---|---|---|
| `--vfs-selftest` | пакет туда-обратно: размеры 0, 1, 64К±1, многомегабайтные; диапазоны через границы блоков; сжатие вкл/выкл; шифрование вкл/выкл; `List`, `Exists`, регистр, кириллица в пути; запись «удалён» в патче; параллельные чтения с 8 потоков | байт блока изменён → ошибка с именем файла (с шифрованием и без: CRC32C); блок переставлен в другой файл → тег не сходится; чужой ключ → отказ с GUID; без ключа → отказ |
| детерминизм | `--cook` дважды с тем же `shader_list.txt` → пакеты равны байт в байт; копия дерева с другими mtime → те же байты | изменённый JSON → пакет другой, но блоки всех неизменённых файлов совпадают по содержимому (сравнение по файлам, не по смещениям) |
| `tools/check_file_io.py` | 0 прямых чтений контента мимо VFS | вставленный `std::ifstream` в рантайм-файл → 1 находка |
| паритет dev | Release `--vfs=loose` против `--vfs=packages` на 4-5 видах (пляж, роща, ванная днём и ночью, лодки), `--wind-freeze`: доля пикселей > 8 уровней на полу «та же рука дважды»; лог без новых Warning+; то же с `--legacy-barriers` (путь Win10) | пакет без одной текстуры → вид её теряет, гейт ловит |
| дистрибутив на чистом месте | копия `dist/` в папку с кириллицей в пути, `--user-dir` во временную с кириллицей: каждый уровень `--shot`, код выхода 0, в логе 0 Error, 0 `shader permutation not cooked`, кадр против dev-Release на полу; **открытые файлы — по аудиту ОС** (ETW FileIO через встроенный `wpr`), а не по логу VFS: прямой `ifstream` мимо VFS в лог не попадает | переименованный `base.tcpak` → понятная ошибка и MessageBox, не падение |
| чистая машина | Windows Sandbox (встроен в Win11 Pro): без VC++ runtime, без NVIDIA DXCache, без нашей видеокарты (WARP) — сообщения о требованиях, а не падение | — |
| время и память | загрузка (холодный и тёплый кэш ОС) и смена уровня: файлы против пакета; пропускная стриминга; `mem:`; первый вход с пустым PSO-кэшем | — |
| крэш | `--crash-selftest=<рука>`: access violation, terminate на рабочем потоке, abort, purecall, переполнение стека — дамп и MessageBox; fastfail — код выхода и лог (§7: дамп не ждём); символизация по архиву символов даёт строку в `main.cpp` | без PDB той же версии стек не читается — проверка, что архив символов привязан к сборке |

GBV не нужен: пассы, барьеры и ресурсы не меняются. Смена цели шейдеров на фиксированную (§5 п.2) — тот же паритет кадра.

## 10. Шаги

**D0 — решения владельца (§11).** Без них не начинать D2+ (D1 от них не зависит).

**D1 — VFS над файлами.** `core/vfs/` (Loose + абсолютные пути + `WritablePath` = корень репо + широкие пути к ОС), перевод
всех мест §0.1 (включая чтение исходников шейдеров и include: поведение то же) и разделов «по требованию» (Developer Controls,
океан, частицы), ключи mtime → `GetStat().version`, `check_file_io.py`, счётчики и `get_readouts` блок `vfs`, манифест с UTF-8
и `GetCommandLineW` во всех конфигурациях. Готово: кадр и лог dev-Release как до шага (паритет), check_file_io 0, три
конфигурации собираются, `check_logging` / `check_render_knobs` / `check_gpu_alloc` 0. **Самый большой шаг по объёму правок**
(~45 мест, ~25 файлов), поведение не меняется.

**D2 — пакет.** Формат §3, писатель (`--pak-build` из списка файлов), читатель (отображение в память, кэш блоков, CRC32C),
zstd (или zlib), `--pak-list`, `--pak-verify`, монтирование в dev (`--vfs=packages|both`), `--vfs-selftest` без шифрования.
Готово: паритет dev на пакете из ручного списка файлов wind_test, загрузка и стриминг замерены, решено про повторные чтения
`.mesh.bin` (§2.2).

**D3 — шифрование.** CNG AES-256-GCM, HKDF, синтетический nonce от хранимых байт, AAD, ключ вне репо, `PakKey.g.h`, отказ
чужого ключа, руки самопроверки. Готово: `--vfs-selftest` со всеми контрольными руками; расшифровка на загрузке wind_test
замерена.

**D4 — шейдеры.** Идентичность без абсолютных путей и с флагами Release, фиксированная цель (проверка 6.6), `--shipping-sim`,
`--shader-record` / `--vfs-record`, режим `record` и `shader_list.txt` в git, `shaders.tcpak`, страховка по решению, опрос
файлов выключен в Shipping (пересборка PSO ручками — нет), FXC-откат убран в Shipping, кэши в папке пользователя. Готово:
Release `--vfs=packages` со всеми руками записи — 0 промахов; первый вход с пустым PSO-кэшем замерен.

**D5 — сборщик.** Конфигурация `Cook|x64`, `--cook`: обход + записанный список + литералы, отчёт, маски воды с пересчётом
ключа, детерминизм, профили `test` / `release`, `graphics_defaults.json`. Готово: пакет wind_test собран сборщиком, паритет,
отчёт без ошибок, размер известен.

**D6 — конфигурация Shipping.** `TC_SHIPPING` и что вырезается, корень = папка exe, `%LOCALAPPDATA%` до открытия лога,
настройки отличиями и атомарно, крэши на всех потоках, версия/иконка/манифест, проверка железа и MessageBox-ы, DLL-гигиена,
проверка SM 6.6 на Win10 и решение про Agility SDK. Готово: exe с двойного клика из папки вне репо (с кириллицей в пути)
стартует в уровень; без пакета — сообщение, не падение; все руки `--crash-selftest` как в §9.

**D7 — `build_dist.py`.** §8.2, §8.3. Готово: одна команда с чистого дерева → zip; повторный запуск → те же пакеты; отмена
посередине не оставляет ничего в `dist/`.

**D8 — окно Build Distribution и MCP.** §8.4, `--progress=json`, `build_dist` / `build_dist_status`. Готово: из окна (и в
Debug-редакторе) собирается тот же пакет, что из консоли с тем же профилем (байт в байт); отмена убивает дерево процессов;
гейт MCP. Окно снято `--editor --shot` и посмотрено глазами.

**D9 — гейты и документы.** §9 целиком, раздел в AGENTS.md («Distribution — VFS, packages, Shipping»), этот план → статус и
результаты. Коммиты — по слову владельца, каждый шаг отдельно.

### Что ещё нужно полноценному дистрибутиву — отдельными планами после этого

1. **Меню и настройки для игрока.** В Shipping нет Developer Controls, и без меню игрок не поменяет ни окно, ни DLSS, ни
   качество, ни чувствительность мыши. Минимум: Esc-меню (продолжить, настройки, выход) и экран настроек (режим окна и
   разрешение, режим DLSS, пресет качества, яркость/экспозиция, мышь, раскладка клавиш — просмотр), ImGui на первое время.
   **Самое важное из этого списка.**
2. **Пресеты качества** (низкое/среднее/высокое/ультра) — что именно они двигают (RT-видимость неба, GI, VSM, облака, разрешение
   отражений); их список добавится в `recordArms` (§8.0).
3. **Инсталлятор** (Inno Setup или MSIX) или **Steam** (депоты; выравнивание файлов в пакете на 1 МБ под дельта-патчи —
   флаг формата). Инсталлятор же регистрирует WER-модуль для дампов `__fastfail` (§7).
4. **Подпись Authenticode** — без сертификата SmartScreen и антивирусы пугают при первом запуске (зашифрованные пакеты и
   свежий неподписанный exe — частый повод для эвристик); сертификат стоит денег.
5. **Отправка крэшей** (Sentry / Crashpad / свой сервер) — пока дампы лежат локально.
6. **DirectStorage** — когда загрузка упрётся в CPU распаковки.
7. **Проверка на AMD и Intel** — сейчас только NVIDIA.

## 12. Что изменилось после ревью (редакция 2, 2026-11-13)

Независимое ревью (агент, не писавший план, сверил ~20 утверждений с кодом) и моя вычитка. Принято:

- **Шифрование** (§4): nonce считался от несжатого блока и номера файла — смена уровня сжатия повторила бы nonce на других
  байтах под тем же ключом (в GCM это раскрывает ключ аутентификации), добавленный файл перешифровывал бы всё после себя.
  Теперь nonce от хранимых байт, хэш пути вместо номера, nonce и тег хранятся в таблице блоков, AAD против перестановки
  блоков, HKDF разделяет ключи, хэндл ключа на поток. Без шифрования — CRC32C, иначе рука «битый байт» в §9 не работала бы.
- **Сборщик** (§7, §8): отдельная конфигурация `Cook|x64` — exe редактора занят (LNK1104), в Debug шейдеры сварились бы с
  Debug-флагами, и сборщик мог отстать от Shipping по версиям форматов.
- **Запись пермутаций** (§5): не «в Shipping» (там вырезаны нужные ключи), а Release с `--shipping-sim`, по рукам (разрешения,
  DLSS, без mesh shader, без RT, bindless) — прогон одних уровней пропустил бы ветки устройства и разрешения; список в git,
  сборка детерминирована; шаги шейдеров и сборщика переставлены (D4 ↔ D5).
- **Оверлей пользователя** только с префиксом `data/bot_memory/` (§2): на весь корень он отменял бы `allowLoose: false`.
- **Крэши** (§7): обработчик terminate — свой у каждого потока, abort / fastfail минуют фильтр — обработчики на всех потоках,
  честно сказано, что fastfail в процессе не поймать; `device_removed.log` остаётся в Shipping.
- **Факты** (§0): Streamline грузит только DLSS и PCL — список DLL берётся из загруженных модулей; TBB не ищется на машине;
  при провале DXC есть откат на FXC, а не тихая потеря пасса; mimalloc и sln для новых конфигураций; Jolt-define-ы как ABI.
- **Опись** (§0.1): добавлены второе чтение ядра bloom, корона солнца, `data/materials.json`, проба `.dds`, выбирающая
  пермутацию, `exists`-проверки, `scene.replicate`; статический поиск литералов-путей в сборщике. Отклонено: «пути только в
  коде» `Race.cpp:29`, `PlaySession.cpp:361`, `ParticlePresets.h:14` — это комментарии.
- **Детерминизм**: в пакете нет mtime и номера сборки (версия записи = хэш содержимого, ключи масок воды пересчитываются),
  рука гейта сравнивает файлы, а не смещения.
- **Настройки** (§6): пишутся только отличия от дефолтов и атомарно; дефолты — `tools/dist/graphics_defaults.json`.
- **Пути с кириллицей** (§2, §6, §9): широкие вызовы, папка пользователя до лога, манифест UTF-8 во всех конфигурациях, гейт с
  кириллическим путём; аудит открытых файлов средствами ОС; Windows Sandbox; путь старых барьеров (Win10) в паритет.
- **Чтения** (§2.2): пакет отображается в память — нет очереди позиционных чтений на одном хэндле; повторные чтения
  `.mesh.bin` решаются по замеру D2; распаковка в потоке стриминга — параллельно при нужде.
- **Мелочи**: запись «удалён» для патчей, временный файл + rename при отмене, `--vfs=loose` определён, `--crash-selftest` в
  списке, `include` без обхода, вопросы 13-15 (лицензия `rocks`, атласы Consolas, минимальные требования).
