# Локальная модель в редакторе: команды естественным языком (WITH_EDITOR)

Цель: набрать «зарой все пальмы» и получить выполненную команду редактора с откатом по Ctrl+Z.
Только `WITH_EDITOR`; в Release-билде не должно остаться ни кода, ни зависимостей, ни файлов модели.

## Почему грамматика НЕ решает задачу (зафиксировано сразу, чтобы не вернуться)

Первая идея была «глагол + квантор + строка в `MatchesSearch`», без всякой модели. Она ломается
на ПЕРВОМ же примере: ассеты зовутся `coconut_palm` / `date_palm` / `curly_palm`, а поиск ищет
подстроку — русское «пальмы» не совпадёт ни одной буквой. Грамматика покрывает ровно то, что
и так набирается в поиске аутлайнера. **Семантика ИМЕНИ — это и есть задача, а не разбор фразы.**

Грамматика остаётся в плане, но НЕ как первый шаг, а как быстрый путь для точных формулировок (E7).

## Выбор модели

Задача узкая: текст → JSON с выбором из ~10 действий и ~124 имён ассетов. Нужны два свойства:
**русский язык** и **структурированный вывод**. Размер здесь даёт мало: выбор из списка,
поданного в промпт, 7B делает практически идеально, и 32B заметно лучше не будет.

| модель | Q4_K_M | где уместна |
|---|---|---|
| Qwen2.5-7B-Instruct | ~4.7 ГБ | **рекомендуемый старт** — потолок качества для этой задачи |
| Qwen2.5-14B-Instruct | ~9 ГБ | если хочется запаса под сложные фразы (условия, исключения) |
| Qwen2.5-32B-Instruct / Mistral Small | 14–20 ГБ | «максимально крутой», но делит VRAM с рендером |
| Qwen2.5-1.5B-Instruct | ~1 ГБ | fallback для слабой машины |

Модель — ПАРАМЕТР, не решение архитектуры: путь к GGUF в настройках, меняется без пересборки.
Список выше — по состоянию на май 2026; перед стартом свериться со свежими релизами.

## Где считать

**CPU по умолчанию.** Команда набирается руками раз в минуту, 1–3 секунды ответа никого не
убьют, зато ноль VRAM и ноль конкуренции с рендером. GPU-режим — опция в настройках для тех, кому
не жалко памяти: там ответ <100 мс, но во время инференса кадр просядает.

## E1. Граница: `EditorIntent`, а не «нейронка в редакторе»

Один интерфейс: строка → `EditorIntent { action, filter, quantifier, params }`. Реализаций две — `LlmIntent`
и `GrammarIntent`. Весь остальной редактор знает только про `EditorIntent` и не знает, откуда он взялся.
Это то, что позволяет выкинуть модель целиком и оставить фичу работать.

## E2. Рантайм инференса — ОТДЕЛЬНЫЙ ПРОЦЕСС

`llama-server` из llama.cpp, поднимается лениво при первом запросе, общение HTTP по localhost.

Почему не линковать в процесс:
* в движок не приезжает ни одной новой зависимости — ни в Release, ни в Release_Editor;
* падение или OOM в инференсе не роняет редактор с несохранённым уровнем;
* модель и рантайм обновляются отдельно от движка;
* секунда инференса делает цену IPC незаметной.

Запрос асинхронный, кадр не блокируется никогда. Модель в репозиторий НЕ кладётся — скрипт
скачивания в `tools/`, путь в настройках редактора.

## E3. Схема команд + GBNF: выдумать имя ФИЗИЧЕСКИ НЕЛЬЗЯ

Ответ ограничен **GBNF-грамматикой**: на каждом шаге сэмплинга разрешены только токены,
допустимые грамматикой. Это не «обычно валидный JSON», а гарантия.

**Главный ход шага: грамматика ГЕНЕРИРУЕТСЯ ИЗ УРОВНЯ** — в неё перечисляются ЛИТЕРАЛАМИ
реальные имена ассетов и допустимые действия. Галлюцинация несуществующего ассета становится
невозможной не по уговору, а по построению. Это тот же принцип, что и с барьерами: лучше
корректность по конструкции, чем проверка постфактум.

## E3.1. ТРИ ВЕТКИ ОТВЕТА: модель обязана уметь сказать «такого API нет»

Требование владельца, и оно вскрывает прямое противоречие в E3. Грамматика, перечисляющая
ТОЛЬКО существующие действия, делает честный отказ **физически невыразимым**: на запрос
«покрась все пальмы в красный» модель ОБЯЗАНА выбрать что-то из списка и подставит ближайшее —
например `bury`. Это ХУЖЕ галлюцинации: команда валидна, исполнима и не та.

Поэтому грамматика разрешает ТРИ формы ответа, и выбор между ними — часть задачи модели:

```
{"kind":"command",   "action":"bury", "filter":["coconut_palm","date_palm"], "scope":"all"}
{"kind":"needs_api", "requested":"покрасить в красный",
                     "proposed":"setBaseColor(objects, rgba)",
                     "why_existing_dont_fit":"setMaterial меняет весь материал, а нужен только цвет"}
{"kind":"unclear",   "question":"Какие именно деревья имеются в виду?"}
```

Структурные гарантии E3 при этом ЦЕЛЫ: внутри ветки `command` имена действий и ассетов
по-прежнему перечислены литералами и выдумать их нельзя. А `needs_api` — единственное место
со свободным текстом, и он НИЧЕГО НЕ ИСПОЛНЯЕТ по определению — его максимальный эффект
это строка в логе и текст на экране.

### Модель по умолчанию ХОЧЕТ УГОДИТЬ — это надо ломать явно

Главный риск здесь не технический, а поведенческий: instruct-модели обучены быть полезными и
почти всегда предпочтут «близкое действие» честному отказу. Значит в системном промпте
это переворачивается явно и жёстко:

* **`needs_api` ЛУЧШЕ, чем похожее действие.** Невыполненная команда стоит ничего,
  выполненная не та — порченный уровень.
* перед `needs_api` обязана перечислить, какие существующие действия рассмотрела и почему не подошли
  (поле `why_existing_dont_fit`) — это же страховка от ЛОЖНОГО отказа, когда API на самом деле есть;
* список действий в промпте идёт С ОПИСАНИЯМИ, а не одними именами: без них модель
  догадывается о семантике по названию и путает `bury` с «спрятать» (= `setEnabled(false)`).

### Запросы на API НАКАПЛИВАЮТСЯ — это готовый бэклог

Каждый `needs_api` пишется `LOG_INFO` в session-лог вместе с исходной фразой. Через неделю
работы это уже не диагностика, а список «что реально хотелось от редактора, отсортированный
по частоте» — ровно то, по чему стоит расширять API. В UI ответ показывается как
«Такого действия нет. Предлагается: `setBaseColor(objects, rgba)`» — без кнопки «выполнить»,
потому что выполнять нечего.

### Побочное следствие для архитектуры

Раз модель должна рассуждать о ГРАНИЦАХ API, список действий перестаёт быть захардкоженным
списком в промпте и становится **реестром в коде**: имя, описание, параметры, фабрика
`EditorCommand`. Из одного реестра генерируются и GBNF-грамматика, и описания в промпте, и
диспетчер исполнения. Добавление действия = одна запись в реестре, а не три правки в разных
местах, которые обязательно разъедутся.

## E4. Контекст в промпте и кэш prefill

Системный промпт: список действий, список ассетов уровня, типы, текущее выделение, примеры.
Он ПОСТОЯНЕН между запросами, а значит prefill кэшируется и каждый запрос — это десяток токенов
ввода плюс 20–40 токенов генерации. Перестраивается только при смене уровня.

## E5. Резолв селектора — уже существующий код

`intent.filter` → множество объектов через `MatchesSearch` (имя / тип / id / ассет) — тот же путь,
что у поиска в аутлайнере. Модель возвращает ИМЕНА АССЕТОВ, а не свободную строку, так что
никакой новой логики выборки писать не надо.

## E6. Исполнение: ПРЕДПРОСМОТР и только через CommandStack

Модель НИЧЕГО НЕ ИСПОЛНЯЕТ. Она возвращает намерение, UI показывает, что понялось и сколько
объектов зацепит: «Bury 247 objects — coconut_palm ×183, date_palm ×64. Выполнить?».
Дальше один `CompositeCommand` через `EditorCommandStack` — то есть Ctrl+Z откатывает ОДНИМ шагом.

Это не паранойя: за эту сессию буквальное понимание «все вершины под поверхностью» уже
утопило пальму на 15 метров. То же самое на 621 объекте без предпросмотра — потерянный уровень.

## E7. Грамматика как быстрый путь

Точные формулировки (`bury coconut_palm`, `delete selected`) разбираются без модели и отвечают
мгновенно. Модель подключается, только когда грамматика не справилась.

## E8. Гейты и деградация

* три конфига собираются БЕЗ модели и без llama.cpp на машине;
* модели нет → поле ввода **УБИРАЕТСЯ**, а не дизейблится (инертный контрол — врущий контрол);
* всё под `#if WITH_EDITOR`, в Release не остаётся ни байта;
* диагностика — `LOG_*` в session-лог (запрос, распознанный intent, число объектов, время), новых
  `logs/<name>.log` не заводить.

## Оценка

| шаг | объём |
|---|---|
| E1 + E5 + E6 (каркас, резолв, предпросмотр, undo) | 1 день |
| E2 + E3 + E4 (сервер, грамматика из уровня, промпт) | 1–2 дня |
| E7 + E8 (грамматика, гейты, UI) | 1 день |

## Чего здесь сознательно НЕТ

Нет «агента», который сам решает цепочки действий, и нет доступа к файлам. Один шаг: фраза →
одна команда редактора.

**Поправлено на шаге 2.** Здесь стояло «нет генерации контента; одна команда над ВЫБОРКОЙ
объектов». Оба ограничения сняты владельцем запросом «рассади 10 новых пальм»: `spawn` создаёт
объекты, а цель команды — не обязательно выборка и вообще не обязательно существующие объекты.
Что осталось в силе: один шаг, никаких цепочек, и файловые операции (save/open/reload) в
словарь не попадают.

## Ход работ

### Шаг 1 — каркас: E1 + E3.1(реестр) + E5 + E6 + E7 + E8. СДЕЛАНО.

Всё, кроме самой модели. Три конфига собираются, гейт зелёный, фича работает через грамматику.

Что появилось:

| файл | что это |
|---|---|
| `sources/editor/EditorObjectMatch.h` | предикат поиска аутлайнера, вынесен в общий заголовок (E5) |
| `sources/editor/intent/EditorIntent.h` | граница `строка → намерение`, три ветки ответа (E1, E3.1) |
| `sources/editor/intent/EditorIntentSource.h` | интерфейс источника намерений |
| `sources/editor/intent/EditorActionRegistry.{h,cpp}` | **реестр действий** — имя, описание, параметры, фабрика команды (E3.1) |
| `sources/editor/intent/GrammarIntentSource.{h,cpp}` | быстрый путь для точных формулировок (E7) |
| `sources/editor/intent/EditorIntentResolver.{h,cpp}` | резолв селектора + предпросмотр + исполнение (E5, E6) |
| `sources/editor/ui/CommandBarPanel.{h,cpp}` | панель `Window > Command Bar` |
| `tools/intent_regression.{cpp,vcxproj}` | headless-гейт слоя намерений |

**Реестр — не список в промпте, а единственная реализация.** Это главное следствие E3.1, и оно
оказалось рефакторингом, а не добавлением: `BurySelectionBelowSurface`, `DeleteSelection`,
`DuplicateSelection`, `SetSelectionEnabled` жили анонимным неймспейсом в `EditorController.cpp` и
работали ТОЛЬКО над `ctx.selection`. Командная строка обращается к тем же действиям над множеством,
которое выборкой не является, а действие, существующее в двух копиях, — это действие, чьи копии
однажды разойдутся в том, что именно они отказываются трогать. Логика (включая двести строк
лучевых проб `bury`) переехала в реестр; в `EditorController` остались обёртки, которые подставляют
выборку и формулировки «ничего не выделено». Пункты меню, End и набранная фраза теперь попадают в
один диспетчер `RunEditorAction` и одну историю.

Действий пять: `select`, `setEnabled`, `delete`, `duplicate`, `bury` — ровно те, у которых уже была
рабочая реализация. Каждое несёт ОПИСАНИЕ для модели; без него `bury` путается со «спрятать»
(`setEnabled false`), что план и предсказывал.

**Два отказа, защищающие уровень**, проверены гейтом: `delete all` без фильтра отвечает вопросом
«какие именно», а не сносит уровень; фильтр, не нашедший ничего, отказывается с причиной. Второй
барьер стоит в резолвере и срабатывает, даже если намерение подделать в обход обоих источников.

### Отклонение от E8, сознательное

E8 требует УБИРАТЬ поле ввода, когда модели нет. Буквально это сейчас означало бы убрать панель
целиком, потому что модели нет вообще. Но грамматика — тоже источник намерений, и она работает
всегда, так что контрол не инертен: он делает ровно то, что обещает подсказка под ним. Правило
реализовано по смыслу, а не по букве: панель регистрируется, только если `AnySourceAvailable()`,
и если однажды не останется ни одного источника, её не будет в `Window` — не серой, а вообще.

### Верификация

* Debug, Release, Release_Editor — собраны чисто (Debug = `/WX`).
* E8 «в Release не остаётся ни байта» проверен НА АРТЕФАКТЕ, а не на слове: `.obj` новых
  файлов в Release — 1.8 КБ (пустая единица трансляции), в Release_Editor — 6–9 МБ.
* `x64/Debug/intent_regression.exe` — PASS, exit 0.
* **Гейт проверен поломкой контроля**: `MatchesSearch` временно лишили разбора свойств ассета →
  гейт упал на `FAIL: coconut_palm matches`; правка отменена, гейт снова зелёный. Без этого
  «PASS» не значил бы ничего.
* `--level=data/levels/atoll.json --shot=... --wind-freeze=0` на Release_Editor — `session end:
  clean shutdown`, скриншот записан.
* `python tools/check_logging.py` — 0 findings.

### Что дальше — шаг 2: E2 + E3 + E4 (модель)

Ничего из написанного менять не придётся: новый источник добавляется в `sources_` списком в
конструкторе `CommandBarPanel`, всё остальное уже говорит на `EditorIntent`.

1. `LlmIntentSource` поверх `llama-server` (отдельный процесс, ленивый подъём, HTTP по localhost).
2. GBNF **из уровня**: имена ассетов и id действий перечисляются литералами из реестра и документа.
3. Системный промпт из того же реестра (`Actions()` уже отдаёт имя + описание + параметры) плюс

4. Путь к GGUF — настройка редактора, скрипт скачивания в `tools/`; модель в репозиторий не кладём.

## Шаг 2 — СХЕМА и словарь B+C. СДЕЛАНО.

Поводом был запрос «рассади 10 новых пальм». Он не помещался, и важно было понять, что именно
не поместилось: **не глагол, а форма схемы.**

### Диагноз: `{action, filter, scope, params}` кодировала ОДНУ форму предложения

«Глагол над существующими объектами, найденными по подстроке». Ломали её не один запрос, а восемь:

| фраза | что ломается |
|---|---|
| «рассади 10 новых пальм» | существительное — **ассет**, а не объекты уровня |
| «замени пальмы на кокосовые» | **два** существительных: селектор + ассет |
| «сделай туман погуще» | существительное — **поле подсистемы**, объектов нет вообще |
| «пальмы в радиусе 50 м от камеры» | фильтр **пространственный**, не подстрочный |
| «масштаб от 0.8 до 1.2» | параметр — **диапазон**, не скаляр |
| «подними на 2 метра» | значение **относительное**, не абсолютное |
| «спрячь всё кроме пальм» | фильтр **отрицает** |
| «сколько пальм на уровне?» | это **вопрос**, команды нет |

Поэтому слоты названы один раз в `EditorIntent`, а действие ОБЪЯВЛЯЕТ, какие из них потребляет:

```
EditorIntent { kind, action, target{ kind, filter, exclude, scope, where, asset, setting }, params }
```

`target.kind` — `Objects | Asset | Environment | None`, и это три РАЗНЫХ источника истины:
документ, `AssetRegistry`, именованная настройка. `Environment` объявлен, но пока ни одним
действием не потребляется — резолвер отказывает явно, а не делает вид, что сработало.

### Второе следствие: параметры тоже нельзя выдумывать

E3 гарантировал, что нельзя выдумать ИМЯ действия. Про аргументы не гарантировал ничего, а
`count: "десять"` ломает ровно так же — только позже и наполовину применённым. Теперь каждый
параметр объявляет тип (`Number/Bool/String/Range/Vec3/Enum`), а `ValidateParams` отказывает
ДО предпросмотра. Там же живут два расширения, обещанные объявлением: одиночное число
становится `[n,n,n]` для Vec3 и `[n,n]` для Range — в ОДНОМ месте, чтобы ни один источник
не должен был про них помнить.

### Словарь: было 5 действий, стало 12

Добавлены семьи **B** (существование) и **C** (трансформ):

| действие | цель | зачем |
|---|---|---|
| `spawn` | Asset | разброс N копий по грунту: вода, обрывы и занятые места отвергаются |
| `replace` | Objects + asset | «замени пальмы на кокосовые», через `SetMeshAssetCommand` |
| `move` / `rotate` / `scale` | Objects | абсолютно (`to`) и относительно (`by`); `scale` относительно **умножает** |
| `randomizeRotation` / `randomizeScale` | Objects | **половина смысла слова «рассади»** |

**Рандомизация — не украшение.** Десять пальм из одного ассета с одним поворотом и одним
масштабом — это десять копий одной пальмы в одинаковой позе; глаз читает повтор раньше, чем
позиции. Поэтому `spawn` сам даёт случайный yaw и множитель размера, а отдельные действия
работают ещё и по уже расставленному вручную.

Правила разброса взяты у `tools/populate_atoll_palms.py`, который уже отвечал на вопрос «что

## Шаг 3 — МОДЕЛЬ: E2 + E3 + E4. СДЕЛАНО.

### Выбор модели: план был прав насчёт «свериться со свежими релизами»

Таблица в шапке — на май 2026, и она устарела. На сентябрь 2026 актуальна линейка **Qwen3.6**

Железо (96 ГБ RAM, RTX 4090, i9-13900K) позволяет взять верхний квант: **UD-Q8_K_XL, 38.5 ГБ**.

Отдельно стоит зафиксировать, что **план сам себе противоречил и оказался прав**: он писал
«размер здесь даёт мало, 7B делает практически идеально». Для выбора действия из списка под
GBNF это так. Запас взят не на выбор действия, а на ПОНИМАНИЕ русской фразы — ровно то, ради
чего модель вообще появилась в плане.

`tools/fetch_intent_model.py` качает модель и llama.cpp (CUDA-сборка, cudart к ней), умеет
докачивать с обрыва и печатает готовый блок настроек. Ни модель, ни рантайм в репозиторий не

### E2 — отдельный процесс

`sources/editor/intent/LlmClient.{h,cpp}` — WinHTTP + `CreateProcessW`. Ни одной новой
сторонней зависимости: WinHTTP системная, и `winhttp.lib` прилинкован ТОЛЬКО в Debug и
Release_Editor. Сервер поднимается лениво при первом запросе, здоровье ОПРАШИВАЕТСЯ
(`/health`), а не ожидается — загрузка 38 ГБ не должна морозить редактор.

**Поток — сырой `std::thread` с `detach`, сознательно мимо системы задач.** Отслеживаемая
задача джойнится в начале следующего кадра, то есть перенос секундной работы на воркер вернул
бы стоп ровно туда, откуда его убирали ([[async-task-primitive-trap]]).

Интерфейс источника стал асинхронным: `Begin` / `Poll` / `Cancel`. Грамматика удовлетворяет его
мгновенно — одна ветка в панели вместо двух.

### E3 — грамматика ИЗ УРОВНЯ

`IntentSchema.{h,cpp}`. Обе половины контракта в одном файле сознательно: грамматика и парсер
одного формата — это два утверждения об одном и том же, и в разных файлах они однажды разойдутся
в имени поля.

На реальном atoll (107 объектов) получается: **15 литералов для фильтра, 14 ассетов для spawn,
2792 байта грамматики**. Имена действий перечислены литералами из реестра, имена ассетов — из
уровня и `AssetRegistry`. Выдумать несуществующее имя нельзя не по уговору, а по построению.

Три ветки ответа (`command` / `needs_api` / `unclear`) — в корне грамматики, то есть честный
отказ физически ВЫРАЗИМ, что и было требованием E3.1.

### E4 — промпт и кэш prefill

`IntentPrompt.{h,cpp}` собирает системный промпт из того же реестра: имя + ОПИСАНИЕ + параметры
с типами. ChatML применяется на нашей стороне, а не серверным шаблоном, — иначе префикс не
байт-в-байт между запросами и `cache_prompt` не попадает. Гейт это и проверяет.

### Что проверено БЕЗ модели

Почти всё, что может сломаться между редактором и llama.cpp, — чистая функция от реестра и
уровня, поэтому гейт закрывает это без единого токена инференса:
каждый id действия присутствует в грамматике литералом; ассет, которого нет, — отсутствует;
обе ветки-без-исполнения на месте; промпт несёт описание каждого действия и фразу
«PREFER needs_api»; два запроса дают байт-идентичный префикс; ответы модели всех трёх видов
читаются, а подделанный `setBaseColor` отвергается; настройки ходят через JSON туда-обратно;
несконфигурированная модель — не ошибка, а состояние с объяснением в одну строку.

Добавлен режим `intent_regression --dump <level> <gbnf> <prompt>` — он пишет ТЕ САМЫЕ байты,
которые уйдут на сервер, чтобы разговор с моделью шёл по контракту, который отгружается, а не
по переписанному от руки.

### Жизнь сервера: измерено, а не угадано

Требование владельца: «если процесс есть — сервер робит, процесса нет — кулдаун минута и
убивается», и при этом «чтобы оперативу не жрало».

* **Сирот не бывает по построению.** Сервер запускается внутри **job-объекта с
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`** и умирает вместе с редактором — при чистом выходе,
  при падении, при снятии из диспетчера, при остановке отладчиком. Ни один путь завершения
  не обязан отработать. Проверено НА АРТЕФАКТЕ: пробник поднял сервер и убил сам себя
  `TerminateProcess` (ни одного деструктора) — сервер умер следом. Контроль был естественный:
  тот же сервер, запущенный скриптом БЕЗ job-объекта, пережил родителя и держал 35.4 ГБ.
* **Простой.** Плюс к этому редактор сам гасит сервер после `idleTimeoutSeconds` (60) без
  запросов. Веб-чат активностью НЕ считается — редактор не видит чужих запросов, и в
  подсказке это сказано прямо.
* **RAM.** `--load-mode mmap` (и НИКОГДА `--mlock`): 38 ГБ — это file-backed page cache,
  который ОС вытесняет под давлением, а не коммит.

**Grace-период на минуту после выхода делать НЕ стал, и вот почему.** Он экономит ровно одно
— прогрев prefill. Замеры (atoll, промпт 2.5k токенов):

| | загрузка | первый запрос | последующие |
|---|---|---|---|
| CPU (`-ngl 0`) | 4.1 с | 21.4 с | 6.0–6.5 с |
| эксперты на CPU, остальное на GPU (`-ngl 99 --cpu-moe`) | 4.4 с | 17.1 с | 3.5–3.7 с |

Загрузка модели — 4 секунды в любом случае (mmap не читает 38 ГБ, он их отображает), и
тёплый перезапуск не быстрее холодного. Значит быстрый перезапуск ПОДХВАТЫВАЕТ за 4 секунды,
а дорогой там только первый запрос — это prefill системного промпта. Grace-период сэкономил бы
~14 с один раз за сессию, а стоил бы сторожевого процесса, который сам может осиротеть, —
то есть ровно той гарантии, ради которой всё и делалось. Вместо этого взято то, что
измерилось: `--cpu-moe` едет на существующей ручке `gpuLayers` (одна ручка, а не вторая,
которую можно выставить неправильно), давая 6.0 → 3.5 с на запрос.

### Разговор с моделью: два открытия, которые стоили итераций

1. **Каждое правило GBNF обязано быть на ОДНОЙ строке.** llama.cpp заканчивает правило на
   переводе строки, так что продолжение с `|` — не красивое форматирование, а ошибка разбора,
   и сервер отвергает всю грамматику одной фразой «failed to parse grammar», не называя ни
   правила, ни строки.
2. **Qwen3.6 — думающая модель**, а грамматика требует JSON с первого токена: рассуждение и
   намордник дерутся за каждый токен. Лечится подстановкой ПУСТОГО `<think></think>` в хвост
   промпта — он часть промпта, грамматика его не видит.

### Намордник СНЯТ с имён — сознательная отмена части E3

E3 требовал перечислять имена ассетов литералами, «чтобы выдумать было физически нельзя».
На именах это воспроизводит ровно ту беду, от которой писался E3.1, на уровень ниже:
грамматика, разрешающая только пятнадцать строк этого уровня, не оставляет модели способа
сказать про шестнадцатую — она ОБЯЗАНА выдать одну из пятнадцати, и ближайшая неверная
неотличима от верной. «Спрячь камни» в уровне с неожиданно названным камнем спрятал бы пальмы.

Закрытые множества остались закрытыми (id действий + `needs_api` как выход, scope, anchor),
имена стали подсказкой в промпте, а отказ по неизвестному имени даёт РЕЗОЛВЕР, поимённо
(«No mesh asset matches 'X'»).

## Шаг 4 — семья E: окружение. СДЕЛАНО.

### 270 ключей `--set` — ловушка, а не подарок

Прошлый шаг записал их как «готовый словарь». При ближайшем рассмотрении — нет: `--set` пишет
прямо в рантайм-состояние. Правка, сделанная так, **не видна документу, отсутствует в стеке
отмены и исчезает при следующей загрузке уровня**. Правка, которую нельзя отменить, хуже
правки, которую нельзя сделать.

Настоящий словарь оказался ближе и лучше: `properties` сущности окружения — это **секция
уровня дословно**, и редактор уже правит её через `EditEnvironmentCommand` (отменяемо,
сохраняемо). Значит список настроек **порождается из уровня**, ровно как список ассетов:
`sources/editor/intent/EnvironmentSettings.{h,cpp}` обходит `document.Environment()` и отдаёт
листья с их ТЕКУЩИМИ значениями и типами.

На atoll получается 90+ настроек: `wind.strength = 0.2`, `camera.hfovDeg = 90`,
`directionalLight.sunIlluminanceLux = 20000`, `ocean.enabled = true`, `ocean.render.*` и т. д.

### Действие `setEnvironment`

`target.setting` + ровно ОДИН из `params.value` (абсолютное) или `params.scale` (множитель
текущего). Оба сразу или ни одного — отказ: «сделай туман погуще» и «поставь туман 0.02» —
разные просьбы, и молча выбирать между ними значит портить вид.

Тип настройки — контракт: булеву, которой подсунули `1`, валидатор отвергает, иначе она станет
числом в файле уровня и тихо перестанет читаться. Появился вид параметра `Any` — не «что
угодно», а «тип знает более поздняя проверка, и её сообщение точнее».

**Предпросмотр показывает БЫЛО → СТАЛО** реальными числами (`wind.strength: 2 -> 3`), и считает
их тем же кодом, что и исполнение: предпросмотр, посчитанный другой арифметикой, — не предпросмотр.

### Промпт: текущие значения важнее имён

Модели показываются настройки **со значениями** — «сделай туман погуще» отвечаемо только
относительно того, что сейчас. Сначала список шёл в порядке документа, и `ocean.render.*`
(десятки тюнинг-ручек) вытеснил `wind.*` и `cameraExposure.*`, удвоив промпт и prefill. Теперь
сортировка «мельче — первым»: резолвер по-прежнему знает глубокие пути по имени, но перечислять
их незачем.

## Шаг 5 — вопросы, записка исполнителю и свободный чат. СДЕЛАНО.

### Семья F: вопрос — это предпросмотр, за которым нет команды

Никакой новой ветки `EditorIntentKind` не понадобилось, и это признак того, что схема из
шага 2 была сделана правильно. Действие `count` объявляет эффект `ReadOnly` — резолвер и так
считает ровно то, что нужно ответить (сколько объектов и какие ассеты), а «выполнять» там
нечего. Панель для такого ответа **не рисует кнопку Run** (она была бы инертным контролом) и
предлагает единственное осмысленное продолжение — «выделить их».

«Ничего не нашлось» для вопроса — это ОТВЕТ, а не ошибка: иначе «есть тут камни?» превращалось
бы в сообщение об отказе.

### Записка исполнителю: у отказа теперь два адресата

Требование владельца. Когда модель отвечает `needs_api`, она в этот момент уже знает, что
просили, какие существующие действия рассмотрела и почему каждое не подошло. Раньше это
становилось строкой в логе, которую никто не читает между сессиями.

Теперь отказ порождает ВТОРОЙ запрос — **без грамматики**, прозой — и результат дописывается в
`docs/editor_api_requests.md`. Это записка тому, кто будет расширять редактор (в этом проекте
обычно агент, читающий `docs/` в начале сессии, а не человек, листающий session-лог).

Шапка файла написана в первую очередь для такого читателя: **это предположения, а не
спецификация**. Модель написала их из одной фразы дизайнера и не видела кодовой базы дальше
реестра действий. Ценно тут не предложение, а факт, что чего-то ХОТЕЛИ, и повторы важнее любой
отдельной записи: три одинаковые просьбы — это фича, одна — настроение.

В промпте записки есть отдельная просьба: если по размышлении существующее действие всё-таки
подошло бы — сказать ЭТО, потому что ошибочный отказ для исполнителя ценнее отполированного
предложения.

Живьём (промпт движка, 11.3 с): модель написала, что дизайнер хотел менять цвет существующих
пальм, не трогая геометрию; что минимальное действие — `setColor(selector, rgba)`; что для
этого редактору нужны **per-instance material overrides, которых в текущей системе статических
мешей нет**; и что `replace` слишком груб, потому что требует заранее сделанных красных ассетов
и раздувает их число. Это ровно то, что хочется прочитать как исполнитель.

### Свободный чат — отдельной панелью, и намеренно

`Window > Model Chat`. Ни грамматики, ни реестра действий, ни предпросмотра — просто разговор.

Он стоит РЯДОМ с командной строкой, а не внутри неё, потому что это разные вещи. Командная
строка — одна фраза, один ограниченный ответ, одна отменяемая команда и предпросмотр между
ними; именно эта форма делает безопасным наведение на 600 объектов. У чата нет цели, нет
предпросмотра и нечего отменять. Слияние дало бы либо кнопку Run у разговора, либо разговор за
кнопкой Run.

Сервер общий: вторая панель — это не вторая модель на 38 ГБ. Разговор СЧИТАЕТСЯ активностью,
поэтому idle-таймер не унесёт сервер посреди беседы.

### Найдено разговором: размышление съедает весь бюджет

Qwen3.6 думает перед ответом, и `<think>`-блок тратится из того же `n_predict`. У записки с
бюджетом 400 всё ушло на рассуждение о том, как писать записку, а сама записка не появилась.

* **Записке размышление не нужно** — она пересказывает уже принятое решение, а не принимает
  новое. Движок и так гасит `<think>` (`ApplyChatTemplate` с шаблоном `chatml`); провалился
  мой ТЕСТ, который строил промпт руками мимо движка. Урок не про код, а про проверку:
  тест, собирающий запрос сам, проверяет не тот путь, который отгружается.
* **Чату размышление нужно**, поэтому бюджет поднят до 2048, а обрыв теперь ВИДЕН:
  llama-server отдаёт `stopped_limit`, панель говорит «обрезано на лимите токенов». Ответ,
  молча оборвавшийся на полуслове, — та же тихая ложь, от которой защищает остальной слой.

## Шаг 6 — максимум по токенам, и ПОПРАВКА к шагу 4

### Максимум измерен, а не назначен

Владелец попросил дать модели максимум. «Максимум» прячет два разных числа, и только одно
из них чего-то стоит:

* **Контекст `-c`** — выделение KV-кэша, платится один раз при старте:

  | `-c` | private bytes | загрузка |
  |---|---|---|
  | 8192 | 4.5 ГБ | 4.3 с |
  | 32768 | 5.3 ГБ | 4.3 с |
  | 131072 | 7.4 ГБ | 4.3 с |
  | **262144** | **10.2 ГБ** | 4.6 с |

  Поставлен **262144** — родной контекст модели. При 96 ГБ RAM нет причин просить её что-то
  забывать. Эти же числа — доказательство утверждения про mmap, которое раньше было только
  декларацией: 4.5 ГБ приватной памяти против модели в 35.8 ГБ.

* **`n_predict`** — бюджет ВРЕМЕНИ, платится с каждого ответа. Генерация измерена: **28.4
  ток/с** (эксперты на CPU, остальное на GPU). То есть 8192 токена ≈ 4.8 минуты. Чат
  получил 8192 по умолчанию и потолок ползунка 32768, а рядом с ползунком панель показывает
  оценку в секундах — **по скорости, с которой реально шёл прошлый ответ**, а не по числу,
  измеренному на чужой машине. У командной строки лимит поднят до 1024, и это не стоит
  ничего: под грамматикой генерация останавливается, когда JSON закрылся.

### ПОПРАВКА: «туман погуще» был пограничным случаем, а не демонстрацией

Шаг 4 записал отказ `needs_api` на «сделай туман погуще» как подтверждение тезиса E3.1 в
поле. На максимальном контексте та же фраза стала отвечать `ocean.render.fogDensity` scale
1.5, и первая моя гипотеза была — виноват контекст.

**Контролируемый A/B опроверг гипотезу**: один скрипт, одни и те же байты грамматики и
промпта, температура 0, кэш промпта выключен (общий кэш — это разделяемое состояние между
плечами), `-c 8192` против `-c 262144` — ответы совпадают на всех трёх фразах. Переключило
решение то, что между теми двумя прогонами **вырос промпт** (13278 → 13782 байта), когда
добавилось действие `count` со своим примером.

Что из этого следует честно:

* отказ на «туман погуще» был **пограничным**, а не устойчивым, и подавать его как
  доказательство работы механизма было преувеличением;
* устойчивое доказательство — «покрась пальмы в красный»: `needs_api` во ВСЕХ прогонах, на
  обоих контекстах и на обоих промптах;
* и более общий вывод, который стоит держать в голове: **добавление действия в реестр меняет
  промпт, а значит может сдвинуть пограничные решения по другим фразам.** Это не баг схемы —
  это цена того, что промпт генерируется из реестра. Но это значит, что набор фраз-примеров
  надо прогонять после каждого расширения словаря, а не только после правок промпта.

## Шаг 7 — семья A: isolate, frame, selectSimilar. СДЕЛАНО.

### `isolate` заслужил отдельную запись, хотя сначала я решил иначе

На шаге 2 я отказался его делать: «это же `setEnabled false` с `exclude`». Неверно, и разница
ровно та, из-за которой такие вещи и ломаются. `setEnabled false` с исключением ПРЯЧЕТ
остальных, но не ТРОГАЕТ цели — а если кто-то час назад спрятал пальмы, «оставь только пальмы»
покажет пустой остров. Изолировать — это два утверждения: эти ВКЛЮЧИТЬ, всё прочее ВЫКЛЮЧИТЬ, и
забывают обычно вторую половину.

Гейт проверяет именно её: одна из целей заранее спрятана, и после изоляции она обязана стать
видимой. Контроль сломан намеренно (убрал показ, оставил только сокрытие) → `FAIL: the hidden
target was SHOWN, not left hidden`.

### `frame` — камера, и новый вид эффекта

`EditorActionEffect::ViewChange`. Не правка документа (где пользователь смотрит — не часть
уровня), значит не отменяется и НЕ ДОЛЖНА этого обещать. Панель раньше подписывала всё
неотменяемое как «selection only»; теперь подпись зависит от эффекта, потому что «двигает
камеру» и «меняет выделение» — разные обещания.

`FrameSelection`/`TryGetSelectionFrameTarget` переехали из анонимного неймспейса
`EditorController` в `sources/editor/EditorFraming.{h,cpp}` — по той же причине, что и bulk-
действия: клавиша F и фраза «покажи мне пальмы» обязаны двигать камеру одинаково. И «покажи» —
просьба ПОСМОТРЕТЬ, а не выделить: гейт проверяет, что выделение после `frame` не изменилось.

### `selectSimilar` — фильтр приходит из РЕДАКТОРА, а не из фразы

«Выдели все такие же» модель ответить не может: она не видит выделения. Класть выделение в
промпт нельзя — оно меняется постоянно, и prefill-кэш обнулялся бы на каждый клик.

Поэтому в `EditorActionDesc` появился флаг `filterFromSelection`: резолвер сам собирает фильтр
из ассетов выделенного. Декларативно, без сравнения id действия со строкой. Поле добавлено
ПОСЛЕДНИМ в структуре — иначе агрегатная инициализация всех существующих записей молча
съехала бы на одно поле.

Пустое выделение — не «выделить весь уровень», а просьба сначала что-нибудь выбрать.

### Живая проверка: 14 из 14, и это была проверка НЕ ТОЛЬКО новых действий

Урок шага 6 применён: набор фраз теперь включает **все ранее опубликованные ответы**, потому что
новое действие меняет промпт и может сдвинуть пограничное решение о другой фразе. Прогон после
