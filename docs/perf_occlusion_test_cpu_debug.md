# CPU-кадр в Debug: occlusion_test, 2026-09-04

Замер показывает резерв прежде всего в D3D12 debug layer и подготовке RT-структур.
Occlusion в штатном Debug на стартовой камере полезен: его отключение увеличивает CPU-кадр.
Изменений поведения движка по результатам исследования не оставлено.

## Условия и методика

- Debug x64, WITH_EDITOR; штатный D3D12 debug layer включён, GBV не включался.
- `data/levels/occlusion_test.json`, стартовая камера уровня, без движения камеры.
- 625 записей уровня: 624 staticMesh, в том числе 610 пальм, и freeCameraStart.
- Текущие graphics_settings: Legacy CSM, DLSS Balanced, async compute, RT reflections, RT wind radius 40 м.
- `--wind-freeze=0`: фиксирует время анимации, но не отключает запись deform/refit.
- После 20 секунд прогрева записаны 3200 кадров встроенным CPU-профайлером.
- Временный диагностический переключатель менял режим каждые 400 кадров:
  baseline → RT wind off → baseline → occlusion off. Первые 50 кадров каждой фазы исключены.
  Итог: 1400 baseline-кадров и по 700 кадров каждого диагностического режима.
- Повторные отдельные запуски baseline давали 4,21–5,73 мс. Поэтому сравнение wind/occlusion
  ниже сделано внутри одного процесса; абсолютное время зависит от текущей нагрузки машины.
- Для разделения затрат использовались временные CPU scopes в RtSceneAs и BeginThreadCommandList.
  Их собственные накладные расходы включены в замеры. Время записи JSON после захвата не является
  временем исследуемых кадров.

## CPU-кадр с D3D12 debug layer

| Режим | Среднее, мс | Медиана, мс | p95, мс |
|---|---:|---:|---:|
| Штатный | 5,784 | 5,778 | 7,036 |
| RT wind off | 5,076 | 5,094 | 5,897 |
| Occlusion off | 6,312 | 6,301 | 7,669 |

Отключение RT-ветра экономит около 0,71 мс / 12% CPU-кадра, но меняет геометрию отражений.
Это измерение стоимости функции, а не достигнутое ускорение с сохранением качества.
Отключение occlusion добавляет около 0,53 мс / 9%. Уменьшение его собственного CPU scope
не означает ускорения всего кадра: растёт дальнейшая запись/отправка рисования.

`Renderer::WaitForFrame` — около 0,0005 мс: ожидание frame fence практически отсутствует.
Основное время уходит на подготовку/запись/отправку команд и ожидание CPU-задач.

## Где расходуется время

| CPU scope | Штатный Debug, мс/кадр | Без D3D12 debug layer, мс/кадр |
|---|---:|---:|
| Pass_BuildAS, целиком | 1,839 | 1,027 |
| RT.GatherInstances | 0,725 | 0,563 |
| RT.RecordWind | 0,751 | 0,232 |
| RT.BuildTlas | 0,111 | 0,082 |
| RT.BindWindSlots | 0,051 | 0,043 |
| RT.ScreenReuseFlags | 0,060 | 0,053 |
| CL.AcquireListReset, сумма по потокам | 2,918 | 0,354 |
| CL.AcquireAllocator, сумма по потокам | 0,018 | 0,014 |
| CL.SetDescriptorHeaps, сумма по потокам | 0,080 | 0,021 |
| Service3: отправка команд/queue synchronization | 0,870 | 0,310 |
| Scene::PrepareViews, основной поток | 0,665 | 0,587 |
| Pass_OcclusionQueries | 0,435 | 0,127 |

Scopes включают вложенные scopes, а работа разных потоков перекрывается. Строки таблицы
нельзя складывать: 2,918 мс Reset — сумма 32 вызовов на разных потоках, не 2,918 мс
последовательной задержки CPU-кадра. Пулы command allocator/list уже имеют fast path без mutex;
основная стоимость открытия списка находится в AcquireCommandList/Reset.

В отдельном процессе с тем же Debug-кодом и DRED, но без включения D3D12 debug layer,
штатный CPU-кадр составил 3,410 мс (медиана 3,291; p95 4,477), против 5,784 мс в процессе
со слоем. Это примерно 2,37 мс / 41% наблюдаемой разницы, не универсальная гарантия.
В этом режиме RT wind off дал 3,184 мс, а occlusion off — 3,376 мс: occlusion уже почти
нейтрален по CPU. Компиляторная конфигурация оставалась Debug; проверки D3D12 — нет.

## Приоритеты оптимизации

1. **Неизменные данные RT-объектов.** `sources/rendering/rt/RtSceneAs.cpp:186` каждый кадр
   обходит все объекты, получает instance/material данные и считает material fingerprint.
   Бюджет gather — 0,56–0,72 мс. Следующий шаг — кэш описаний по явным версиям transform,
   material, visibility и состава сцены, оставив динамическими выбор wind slots и обновление
   анимированной геометрии. Важно сохранить индивидуальные material records объектов и
   инвалидировать кэш при редактировании/перезагрузке. Весь бюджет gather сэкономить не получится.
2. **Подготовка wind BLAS и повторные D3D12-вызовы.**
   `sources/rendering/rt/AccelerationStructure.cpp:242` заново строит vector geometry descs и
   запрашивает prebuild info для каждого wind slot. Имеет смысл кэшировать неизменную геометрию
   и размеры, переиспользовать scratch-массивы и объединить staging пары SRV/UAV в RtSceneAs.
   `BuildTlas` также каждый кадр получает prebuild info и пересоздаёт SRV при стабильном адресе.
   Измерены 0,75 мс всего RT.RecordWind; доля, устранимая такими кэшами, ещё не измерена.
   Deform/refit нельзя просто пропускать на неподвижной камере: ветер продолжает анимироваться.
3. **Уменьшение числа command list и submission-вызовов с сохранением параллелизма.**
   `sources/rendering/core/Renderer.cpp:1111` и `:1236` показывают значительную зависимость от
   D3D12 validation. Проверять объединение коротких совместимых проходов через существующий
   CLGroup, учитывая зависимости и полезное перекрытие; пулы allocator сейчас не приоритет.
4. **Отдельный режим Debug без D3D12 validation** может быть полезен для отладки логики приложения.
   Это явная смена диагностического режима, а не замена обычного Debug с проверками рендера.
   Постоянного переключателя в рамках исследования не добавлялось.

Scene::Tick (~0,12 мс), BeginImGuiFrame (~0,09 мс), wind slot selection (~0,05 мс) и повторная
проверка screen-reuse flags (~0,06 мс) существенно меньше основных участков.

## Артефакты и состояние проекта

- `traces/trace_20260904_165935_debug_000.json` — цикл режимов, D3D12 debug layer включён.
- `traces/trace_20260904_170039_debug_000.json` — такой же цикл без D3D12 debug layer.
- `logs/session_20260904_165850_48084_debug.log` и
  `logs/session_20260904_170002_6280_debug.log` — события фаз; session logs подлежат ротации.
- Для базового воспроизведения штатным бинарником:
  `x64/Debug/test_cube.exe --level=data/levels/occlusion_test.json --trace=1500 --shot-delay=20 --wind-freeze=0`.
  Дополнительные scopes и циклическое переключение использовались только во временной сборке.
- После захвата процессы зависали при shutdown: последняя запись Streamline —
  `slOnPluginShutdown: Shutting down NGX`. После ожидания они завершались принудительно;
  clean-shutdown footer поэтому отсутствует. Зависание относится к завершению, а не к
  исследуемым кадрам; одновременно два захвата в итоговых сериях не работали.
- Все временные изменения C++ восстановлены побайтно, штатный Debug x64 успешно пересобран.
  Оставлен только этот отчёт; уже существовавшие/параллельные изменения других файлов не трогались.
